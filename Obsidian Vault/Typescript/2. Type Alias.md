To your question: TypeScript doesn't _need_ an explicit return type annotation because it has **return type inference**. When you write:

```ts
export function greetCustomer(name: string) {
  return `Hello ${name}, welcome to Support.ai! How can I assist you today?`;
}
```

TypeScript looks at the `return` statement, sees it's returning a template literal (which is always a `string`), and automatically infers the return type is `string`. It's functionally identical to writing:

```ts
export function greetCustomer(name: string): string {
  return `Hello ${name}, welcome to Support.ai! How can I assist you today?`;
}
```

This is why your `SupportResponse` type alias works even without explicit annotations — TypeScript checks the _inferred_ signature of `greetCustomer` against `(name: string) => string` and confirms they match structurally. That structural matching is exactly what the lesson's tip was referring to.

**Why you might still want explicit return types:**

1. **Documentation** — Readers immediately see what a function returns without tracing through the logic.
2. **Safety net** — If someone later edits the function and accidentally returns the wrong type, the explicit annotation catches the mistake immediately rather than silently changing the inferred type.
3. **Complex functions** — When a function has multiple return paths (e.g., conditional returns), explicit annotations prevent TypeScript from inferring an overly broad or incorrect union type.

For example, without an explicit annotation, this function's inferred return type might surprise you:

```ts
function getValue(condition: boolean) {
  if (condition) {
    return "yes";
  }
  // no return here - falls through!
}
// inferred return type: string | undefined
```

Good observation — you're right that in your `utils.ts` file, `SupportResponse` isn't directly annotated on `greetCustomer` or `farewellCustomer`. It's exported, but not explicitly used as a type annotation in that file.

Look at where it actually gets used, though — in the test file:

```ts
const _greetResponseTest: SupportResponse = greetCustomer;
const _farewellResponseTest: SupportResponse = farewellCustomer;
```

This is where the real work happens. These lines take your functions and assign them to variables explicitly typed as `SupportResponse`. TypeScript then checks: "Does `greetCustomer`'s signature structurally match `(name: string) => string`?" If your function had the wrong signature (like accepting a second `age: number` parameter, as it did in the starter code), this assignment would fail to compile, and you'd get a type error before any test even runs.

So `SupportResponse` acts as a **contract enforcement mechanism** here. It's not just documentation — it's used to verify (at compile time) that your functions conform to a specific shape, without the test file needing to redeclare that shape or hardcode it into each function.

This is a common pattern in real codebases: define a type alias once, then use it in tests, interfaces, or other functions to enforce consistency across your code. It decouples "what shape does this function need to have" from "how is this function implemented."

If you want to see this fail, you could temporarily change `greetCustomer` to accept an extra parameter and rerun the tests — TypeScript would complain about the assignment in the test file even before the runtime assertions execute.
