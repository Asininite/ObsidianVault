# Deploying Django Applications

## 1. Development vs. Production Servers

- **Development Server:** The server started via `python manage.py runserver` is a minimal, lightweight server meant _only_ for local development and rapid testing. It is not secure, scalable, or dependable enough for public traffic.
    
- **Production Servers:** To deploy a reliable Django app, you must use production-grade web servers like Nginx or Apache. Because these servers are typically written in C (not Python), Django requires a special interface to communicate with them.
    

## 2. Web Server Interfaces (WSGI vs. ASGI)

Django communicates with production web servers using standardized Python gateway interfaces. When you run `startproject`, Django automatically generates configuration files for both.

### A. WSGI (Web Server Gateway Interface)

- **What is it?** The traditional Python standard for communicating between web servers and applications.
    
- **Architecture:** Supports **synchronous** code only (handles one request at a time per thread).
    
- **Entry Point:** Uses the `wsgi.py` file to declare the application callable.
    
- **Popular WSGI Servers:** Gunicorn, uWSGI, Apache (via `mod_wsgi`).
    

### B. ASGI (Asynchronous Server Gateway Interface)

- **What is it?** The modern successor to WSGI.
    
- **Architecture:** Supports **asynchronous** code, allowing the server to handle multiple requests concurrently without blocking (great for WebSockets or long-polling).
    
- **Entry Point:** Uses the `asgi.py` file to declare the application callable.
    
- **Popular ASGI Servers:** Daphne, Uvicorn, Hypercorn.
    

## 3. Cloud Deployment Options

Deploying an app involves configuring runtimes, OS, networks, and databases. Modern cloud computing provides several ways to host your application:

- **1. Virtual Machines (IaaS - Infrastructure as a Service):** * You rent a raw server from a cloud provider.
    
    - **Process:** Highly manual. You must install the OS (e.g., Ubuntu), Python, web server (Apache/Nginx), install dependencies, and configure the environment yourself.
        
- **2. Platform-as-a-Service (PaaS):** * **Process:** Streamlined deployment. You push your code to a Git repository (like on Heroku), and the platform automatically handles the server provisioning, environment setup, and deployment process.
    
- **3. Containerization:** * **Process:** You package your Django app and its exact environment/dependencies into Docker containers.
    
    - These containers can then be deployed and managed using orchestration tools like **Kubernetes (K8s)** or serverless container platforms like IBM Cloud Code Engine.
        

## 4. Database Configuration

Django supports a variety of relational databases.

- **Supported Databases:** PostgreSQL, MySQL, MariaDB, Oracle, and SQLite.
    
- **Hosting Options:** You can deploy them as self-managed (installing the DB on your own VM) or use a DBaaS (Database-as-a-Service) where the cloud provider manages backups and scaling.
    

## 5. Best Practices for a Production-Ready Django App

Before exposing your Django app to the public on the cloud, strictly follow these practices to ensure security, scalability, and reliability:

1. **Use a Production Database:** * **Rule:** _Never use SQLite in production._ It is file-based and not designed to handle high concurrency or heavy web traffic.
    
    - **Solution:** Migrate to a robust relational database like PostgreSQL or MySQL.
        
2. **Secure Credentials:** * **Rule:** Never hardcode passwords, secret keys, or database credentials directly into your `settings.py` file.
    
    - **Solution:** Store sensitive information in **Environment Variables** (`.env` files).
        
3. **Use HTTPS:** Ensure all communication between the web server and the user's browser is encrypted using SSL/TLS certificates.
    
4. **Offload Static and Media Files:** * **Rule:** Do not let your Django app serve CSS, JS, or user-uploaded media in production (it wastes backend resources).
    
    - **Solution:** Use a Cloud Storage service (like AWS S3 or IBM Cloud Object Storage) paired with a CDN (Content Delivery Network) to serve these files efficiently.
        
5. **Load Balancing & Horizontal Scaling:** * **Concept:** Django applications are _stateless_ (they don't store session data in memory by default, relying on the DB/cache instead).
    
    - **Solution:** Take advantage of this by scaling _horizontally_ (adding more instances/containers as traffic increases) and putting a Load Balancer in front of them to distribute incoming traffic evenly.
        
6. **Monitoring and Logging:** Set up robust error monitoring (like Sentry) and server logging to track traffic, diagnose crashes, and monitor performance.
    

### _Additional Django-Specific Security Steps (Context):_

- **`DEBUG = False`:** _Always_ turn off Debug mode in `settings.py` before deployment. Leaving it on exposes highly sensitive application source code and stack traces to end-users if an error occurs.
    
- **`ALLOWED_HOSTS`:** Once `DEBUG = False`, you must specify your live domain names/IP addresses in the `ALLOWED_HOSTS` list in `settings.py` to prevent HTTP Host header attacks.
