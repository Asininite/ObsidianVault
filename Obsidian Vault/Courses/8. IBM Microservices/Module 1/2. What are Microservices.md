# What are Microservices?

## 1. Introduction: The Microservices Architecture

- **Definition:** Microservices architecture is a cloud-native approach in which a single, large application is built as a suite of **many loosely coupled, independently deployable smaller services**.
    
- **The Monolith Comparison (Context):** * _Traditional (Monolithic) App:_ All code (UI, business logic, database access) is bundled into a single unit and deployed all at once. If one small part breaks, the whole app might crash.
    
    - _Microservices App:_ The application is broken down into modular pieces. The shopping cart, the user profile, and the billing system are all separate, independent mini-applications that just talk to each other.
        

## 2. Core Characteristics of Microservices

- **Organized by Business Functionality:** Services are divided based on what they _do_ for the business (e.g., an "Inventory Service" or a "Shipping Service").
    
- **Bounded Context:** The strict line separating these services is called a _bounded context_. It means a service only knows about and controls its own specific domain, and external services cannot directly access its internal workings.
    
- **Independent Technology Stacks (Polyglot Programming):** * Because services only communicate over standard network protocols, they don't need to be written in the same language.
    
    - _Example:_ Team A can build the AI recommendation engine in Python, while Team B builds the high-speed transaction processor in Go. Each team chooses the best tool for their specific job.
        
- **Independent Databases:** Crucially, each microservice usually manages its _own_ database and data model. This prevents a single database bottleneck and ensures that one team changing a database schema doesn't break another team's code.
    

## 3. How Microservices Communicate

Since they are independent, microservices must communicate over a network to function as a cohesive application. They do this via:

- **REST APIs:** Used for synchronous, direct requests (e.g., Service A asks Service B for a user's profile and waits for the response).
    
    - _Limitation:_ API calls are great for getting an initial state, but they are inefficient for staying up-to-date on ongoing progress (because you would have to constantly ask, "Are you done yet?").
        
- **Event Streaming & Message Brokers:** Used for asynchronous communication.
    
    - _Context:_ Instead of direct API calls, a service can broadcast a "state change" event (e.g., "Order #123 was paid") to a message broker (like Apache Kafka or RabbitMQ). Other services that care about this event can listen to the broker and react automatically. This greatly assists in scaling because services don't get bogged down waiting on each other.
        

## 4. Scaling Microservices

- **Horizontal Scaling ("Scaling Out"):** Microservices rely heavily on horizontal scaling, which means adding _more instances_ (replicas/pods) of a service to handle load, rather than making a single instance bigger (Vertical Scaling/Scaling Up).
    
- **Precise Resource Allocation (Cost Savings):** * _In a Monolith:_ If your reporting module is getting heavily used at the end of the month, you have to scale up the _entire_ massive application, wasting resources on the UI and billing modules that don't need it.
    
    - _In Microservices:_ You can scale _only_ the specific component facing the heavy load (e.g., spinning up 10 extra instances of the reporting service, while leaving the rest of the app alone). This drastically reduces infrastructure waste and cloud costs.
        

## 5. Summary of Key Benefits

1. **Agility and Iteration:** You can update code, add features, and deploy changes to one service quickly without touching, rebuilding, or risking the entire application.
    
2. **Resilience (Fault Isolation):** Because they are loosely coupled, a failure in one service (e.g., the email notification service goes down) does not necessarily crash the other services (e.g., users can still browse and purchase items).
    
3. **Optimized Teams:** Small teams can own a service end-to-end, choosing their own tech stack and deployment schedules without being blocked by other departments.
    

## Quick Revision Questions & Answers

**1. What does it mean for microservices to be "loosely coupled"?**

- **Answer:** It means the services operate independently. They don't share source code or databases, and a change or failure in one service does not strictly break or require changes in another.
    

**2. Why might two microservices within the same application be written in completely different programming languages?**

- **Answer:** Because each team can choose the technology stack that is best suited for their specific component's needs (e.g., Python for data science, Node.js for I/O), as long as the services communicate through standard APIs.
    

**3. What is the fundamental difference in how scaling works between monolithic applications and microservices?**

- **Answer:** A monolith requires scaling the _entire_ application if even one feature experiences heavy load, wasting resources. Microservices allow for precise scaling of _only_ the specific component under load.
    

**4. If REST API calls are good for establishing initial state, what is the preferred method for broadcasting state changes across a microservices architecture?**

- **Answer:** Event streaming and Message Brokers (which allow asynchronous communication and continuous progress updates).
    

**5. What is the term used to describe the logical boundary that separates microservices by their specific business functionality?**

- **Answer:** A Bounded Context.
