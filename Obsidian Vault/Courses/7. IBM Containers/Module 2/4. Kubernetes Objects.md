
# Kubernetes Objects Part 1

## 1. What is a Kubernetes Object?

- In software, an object or entity is a bundle of data with a specific identity, state, and behavior.
    
- The term **persistent** means an entity will survive server failures or network attacks (like persistent storage).
    
- **Kubernetes Objects** are persistent entities within the cluster (e.g., Pods, Namespaces, Replica Sets, Deployments).
    
- The **Object Spec** field is provided by the user and strictly dictates the _desired state_ of the object.
    
- The **Status** field is provided by Kubernetes and describes the _current state_ of the object.
    
- The core function of Kubernetes is to constantly work towards matching the current state to the desired state.
    
- You can interact with these objects directly using the Kubernetes API via client libraries or the `kubectl` command-line interface.

## 2. Labels and Selectors

- **Labels** are key-value pairs attached to objects for identification and organization.
    
- A single label does not uniquely identify one specific object; multiple objects can share the exact same labels.
    
- **Label Selectors** are the core grouping method in Kubernetes, allowing you to easily identify and manage a specific set of objects.

![[Pasted image 20260627003341.png]]

## 3. Namespaces

- **Namespaces** provide a mechanism for isolating groups of resources within a single cluster.
    
- They are ideal for large clusters, allowing multiple teams or projects to share a cluster for cost-saving purposes while maintaining strict isolation.
    
- Examples include `kube-system` (intended for system users/processes) and the `default` namespace (used to hold standard user applications).
    
- A namespace provides a scope for naming objects.
    
- Every object must have a unique name for its resource type _within that specific namespace_.
![[Pasted image 20260627003521.png]]

## 4. Pods

- A **Pod** is the absolute simplest and smallest unit in Kubernetes.
    
- It represents a single process or a single instance of an application running in the cluster.
    
- A Pod wraps one or more containers (a Pod specification must contain at least one container).
    
- Creating replicas of a Pod is how you scale an application horizontally.
    
- YAML files are used to define Pods using fields like `kind: Pod` and a `spec` block that details the container's `image` and exposed `ports`.
![[Pasted image 20260627003537.png]]
## 5. Replica Sets

- A **Replica Set** maintains a specific number of identical, horizontally scaled Pod replicas running at any given time.
    
- The `replicas` field specifies the desired number of Pods.
    
- Whenever this field is updated, the Replica Set automatically creates or deletes Pods to meet that desired number.
    
- The configuration includes a **Pod Template** so the Replica Set knows exactly what kind of Pods to create.
    
- It uses a **Selector** (`matchLabels`) to identify which existing Pods it is allowed to acquire and manage.
    
- Creating Replica Sets directly is generally **not recommended**; you should use Deployments instead.
    

## 6. Deployments

- A **Deployment** is a higher-level object that manages Replica Sets and offers significantly better control and features.
    
- Deployments are designed specifically for **stateless applications** (stateful applications should use Stateful Sets instead).
    
- **Rolling Updates** are a critical feature provided by Deployments (but not Replica Sets).
    
- A rolling update smoothly scales up a new version of an application while simultaneously scaling down the old version to zero replicas.
    
- In summary: The Replica Set ensures the appropriate number of Pods exist, while the Deployment orchestrates the rollout of new versions.

## Quick Revision Questions

**1. What are the two main fields of a Kubernetes object, and who provides them?**

The `Object Spec` is provided by the user (defining the desired state), and the `Status` is provided by Kubernetes (defining the current state).

**2. How do Labels and Label Selectors work together?**

Labels are key-value pairs attached to objects for organization, while Label Selectors are the core grouping method used to identify and target a specific set of those labeled objects.

**3. Why would an organization use multiple Namespaces in a single cluster?**

To isolate groups of resources. This allows multiple teams or projects to share a single cluster safely, which saves costs and prevents naming conflicts.

**4. What is the fundamental relationship between a Pod and a Container?**

A Pod is the simplest unit in Kubernetes and acts as a wrapper around one or more containers.

**5. Why is it recommended to create a Deployment rather than creating a Replica Set directly?**

Deployments are higher-level objects that manage Replica Sets for you, offering advanced management features like Rolling Updates to seamlessly transition to new versions of an application without downtime.

**6. Which Kubernetes object is best suited for managing a stateless application?**

A Deployment. (Stateful applications should use Stateful Sets).

# Kubernetes Objects Part 2

## 1. Services Overview

- **Definition:** A Service is a REST object (like a Pod) that acts as a logical abstraction for a set of Pods in a cluster.
    
- **Primary Functions:**
    
    - Provides policies for accessing Pods.
        
    - Acts as a load balancer across the targeted Pods.
        
    - Assigns a single, unique IP address for accessing applications, completely eliminating the need for a separate service discovery process.
        
- **Why are Services needed?** * Pods are highly volatile; they can be destroyed and recreated at any time, leading to constantly changing IP addresses.
    
    - A Service keeps track of these changes and provides a stable IP address or DNS name, utilizing **selectors** to consistently target the correct set of Pods.
        
- **Protocol & Port Support:**
    
    - Supports multiple protocols (TCP is the default, UDP, etc.).
        
    - Supports multiple port definitions (the port number with the same name can vary in each backend Pod).
        
    - Can optionally map incoming ports to specific target ports.
        
- **Application Handling:**
    
    - **Native Kubernetes apps:** API endpoints automatically update when Pod changes are detected.
        
    - **Non-native apps:** Kubernetes uses a virtual-IP-based bridge or load balancer between the application and the backend Pods.
        

## 2. The Four Types of Kubernetes Services

### A. ClusterIP (Default)

- **Accessibility:** Assigns a cluster-internal IP address, making the service reachable **only from within the cluster**. It cannot accept requests from outside.
    
- **Use Case:** Inter-service communication (e.g., communication between the front-end and back-end components of your application).
    

### B. NodePort

- **Mechanism:** An extension of ClusterIP. It automatically creates and routes incoming requests to a ClusterIP service.
    
- **Accessibility:** Exposes the service on _each_ node's IP address at a specific, static port.
    
- **Limitations:** Exposes a single service with no load-balancing requirements for multiple services. **Not recommended for production** due to security purposes.
    

### C. LoadBalancer (External Load Balancer / ELB)

- **Mechanism:** An extension of NodePort. It automatically creates both NodePort and ClusterIP services and integrates with them to direct traffic.
    
- **Accessibility:** Exposes the service to the external Internet using a new ELB with a public IP address.
    
- **Use Case:** Typically utilizes a cloud provider's ELB to host and manage external traffic into the cluster.
    

### D. ExternalName

- **Mechanism:** Maps to a specific DNS name rather than using selectors to find Pods.
    
- **Configuration:** Requires a `spec.externalName` parameter and returns a `CNAME` record and its value.
    
- **Use Case:** Creating a Service that represents external storage, or enabling Pods from completely different namespaces to communicate with each other.
    

## 3. Other Core Kubernetes Objects

### A. Ingress

- **Definition:** An API object that, when combined with a controller, provides routing rules to manage external users' access to _multiple_ services within a cluster.
    
- **Use Case:** In production, it exposes applications to the Internet via port 80 (HTTP) or port 443 (HTTPS).
    
- **Advantage:** While an external load balancer (ELB) is managed outside the cluster and can be expensive, Ingress allows the cluster itself to monitor and manage complex routing efficiently.
    

### B. DaemonSet

- **Definition:** An object that ensures every node (or a specific subset of nodes) runs a copy of a specific Pod.
    
- **Lifecycle:** When new nodes are added to the cluster, Pods are automatically added to them. When nodes are removed, the Pods are garbage collected. If the DaemonSet is deleted, all its associated Pods are removed.
    
- **Use Case:** Ideal for background cluster operations like node monitoring, log collection, or storage daemons.
    

### C. StatefulSet

- **Definition:** An object designed specifically to manage stateful applications.
    
- **Key Features:**
    
    - Manages the deployment and scaling of Pods.
        
    - Provides strict guarantees about the **ordering** and **uniqueness** of Pods.
        
    - Maintains a "sticky" (persistent) identity for each Pod request.
        
    - Provides persistent storage volumes for workloads (so data isn't lost when a Pod restarts).
        

### D. Job (and CronJob)

- **Job:** Creates one or more Pods and tracks the completion process. Jobs are continually retried until they successfully complete their task.
    
    - _Management:_ Deleting a Job removes its Pods. Suspending a Job deletes active Pods until the Job is resumed. Jobs can also run several Pods in parallel.
        
- **CronJob:** An extension of a Job that is used to create Jobs on a regularly iterative schedule (like a Linux cron task).
    

## Quick Revision Questions & Answers

**1. Why do we need Services in Kubernetes if Pods already have their own IP addresses?**

- **Answer:** Pods are volatile and their IP addresses change every time they are destroyed and recreated. A Service provides a stable, persistent IP address or DNS name to reliably access those Pods without needing a separate service discovery mechanism.
    

**2. Which Service type is the default, and what is its primary limitation regarding traffic?**

- **Answer:** **ClusterIP** is the default. Its primary limitation is that it is only accessible from _within_ the cluster and cannot accept external Internet requests.
    

**3. Why is a NodePort Service generally not recommended for production environments?**

- **Answer:** It exposes ports directly on the nodes themselves, which presents security risks, and it lacks built-in load-balancing requirements for managing traffic across multiple services effectively.
    

**4. How does an Ingress differ from a LoadBalancer Service?**

- **Answer:** A LoadBalancer typically exposes a _single_ service to the outside world using a cloud provider's expensive external load balancer. An Ingress provides advanced routing rules to manage external access to _multiple_ services within the cluster using HTTP/HTTPS.
    

**5. If you needed to deploy a log collection agent on every single active node in your cluster, which object would you use?**

- **Answer:** A **DaemonSet**, because it automatically ensures that a copy of a specific Pod runs on all nodes, scaling automatically as nodes are added or removed.
    

**6. What are the two main guarantees a StatefulSet provides that a standard Deployment does not?**

- **Answer:** It guarantees the **ordering** and **uniqueness** of Pods, maintaining a persistent "sticky" identity and persistent storage for each individual Pod.
    

**7. How does a Job handle a Pod that fails to complete its task?**

- **Answer:** The Job will continuously retry creating and running the Pod until the specified task is successfully completed.
