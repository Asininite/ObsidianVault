# Notes on Using Kubectl

## What is Kubectl?

- **Definition:** Kubectl is the official Kubernetes Command Line Interface (CLI).
    
- **Meaning:** It stands for "kube command tool line".
    
- **Core Functions:** It is an essential tool used to deploy applications, inspect and manage cluster resources, view logs, and manage running cluster workloads.
    

## Kubectl Command Structure

- **Syntax:** `kubectl [command] [type] [name] [flags]`
    
- **Command:** Specifies the operation to perform (e.g., `create`, `get`, `apply`, `delete`).
    
- **Type:** Specifies the resource type being targeted (e.g., `pod`, `deployment`, `replicaset`).
    
- **Name:** Identifies the specific resource name (if applicable).
    
- **Flags:** Provides special options or modifiers that override default values.
    
- **Order Requirement:** Keeping these components in this exact order is critical for the command to execute successfully.
    

## The Three Command Types

### 1. Imperative Commands

- **Mechanism:** Allows users to create, update, and delete live objects directly from the terminal. Operations are specified directly as arguments or flags (e.g., passing the image name in the command).
    
- **Pros:** Extremely easy to learn and execute. They are highly ideal for quick development and test environments.
    
- **Cons:** They do not provide an audit trail for tracking changes, lack flexibility due to limited options, do not use reusable templates, and cannot integrate into standard change-review processes.
    
- **Collaboration Issue:** Without a configuration file, developers cannot easily share or reproduce the exact deployment state without manually exchanging the exact commands used.
    

### 2. Imperative Object Configuration

- **Mechanism:** The user runs a command specifying the required operation, optional flags, and a file name containing the full definition of the object in YAML or JSON format (e.g., `kubectl create -f nginx.yaml`).
    
- **Pros:** Produces identical, reproducible results across multiple environments. The configuration files can be stored in source control (like Git), providing an audit trail, change review integration, and reusable templates.
    
- **Cons:** Requires a deep understanding of the object schema and the ability to write YAML/JSON.
    
- **Collaboration Issue:** The user still specifies the exact operation. If a developer manually updates a running object without updating the file, the next deployment using the old file might overwrite or conflict with those changes.
    

### 3. Declarative Object Configuration

- **Mechanism:** Configuration data is strictly stored in files or directories. The user applies the file/directory (e.g., `kubectl apply -f [directory]`), and Kubectl automatically identifies and performs the necessary operations.
    
- **Pros:** This is the ideal method for production systems. It requires no manual operation input from the user. The configuration files define a single "desired state," and Kubernetes automatically calculates the differences and actualizes that state.
    
- **Collaboration Advantage:** Serves as a single source of truth. If updates are missed by a developer, applying the current shared template ensures the cluster perfectly matches the desired expected state.
    

## Commonly Used Kubectl Commands

- **get:** Accesses and lists files, containers, or other resources (e.g., viewing services in a namespace, pods across all namespaces, or specific deployment details).
    
- **delete:** Deletes a specified file, container, or resource.
    
- **autoscale:** Applies the auto-scaling process to a selected resource.
    
- **apply:** Creates or updates resources using YAML or JSON files. It can process multiple files in a directory or fetch configurations directly from a URL.
    
- **scale:** Scales the specific number of replicas for a resource (e.g., scaling a replica set named "foo" or a resource defined in a YAML file to 3 replicas).
    

## Quick Revision Questions & Answers

**1. What are the four mandatory/optional components of a standard Kubectl command, in order?**

**Answer:** Command, Type, Name, and Flags.

**2. Which Kubectl command type is considered the best practice for production environments, and why?**

**Answer:** Declarative Object Configuration. It relies on a single source of truth (configuration files) to define the desired state, and Kubernetes automatically determines the necessary operations to achieve that state without manual user intervention.

**3. What is the main drawback of using simple Imperative Commands for deploying applications?**

**Answer:** They do not use configuration files, meaning there is no audit trail, no integration with version control (like Git), and it makes it very difficult for other developers to reproduce the exact same deployment.

**4. What does the `kubectl apply` command do?**

**Answer:** It creates or updates resources based on the configuration data provided in YAML or JSON files, determining the necessary changes automatically.

**5. In Imperative Object Configuration, what formats must the configuration file be written in?**

**Answer:** YAML or JSON format.
