# Kubernetes Architecture Notes

## Overview of Kubernetes Clusters

- A deployment of Kubernetes is officially called a Kubernetes cluster.
    
- A cluster consists of nodes that run containerized applications.
    
- Every cluster contains exactly one master node (the control plane) and one or more worker nodes (the worker plane).
    
- Nodes are the actual worker machines (virtual or physical) where user applications run.
    
- Nodes are provisioned by the cloud provider, not Kubernetes itself, which allows Kubernetes to remain highly flexible and run on a variety of infrastructures.
    

## The Control Plane (Master Node)

- The control plane acts as the brain of the cluster, maintaining the intended or "desired" state of the system.
    
- It makes global decisions for the cluster, such as scheduling workloads.
    
- It continuously detects and responds to cluster events, such as creating new resources when a fresh application is deployed.
    
- It functions similarly to a thermostat: you set the desired state, and the control plane constantly regulates the system to achieve and maintain that exact state.
    

## Control Plane Components

- **Kubernetes API Server (`kube-api-server`):** The front-end interface for the control plane. All communication within the cluster routes through this API. It accepts commands to view or alter the cluster's state and is designed to scale horizontally by running multiple load-balanced instances.
    
- **etcd:** A highly available, distributed key-value store containing all cluster data and deployment configurations. It is the definitive source of truth for the cluster's desired state.
    
- **Kubernetes Scheduler (`kube-scheduler`):** Responsible for assigning newly created pods to specific worker nodes. It determines the most optimal node based on scheduling principles, configuration options, and available hardware resources.
    
- **Kubernetes Controller Manager:** Runs the background controller processes that actively monitor the cluster's actual state and work to ensure it matches the desired state stored in etcd.
    
- **Cloud Controller Manager:** Runs controllers that interact directly with underlying cloud provider APIs. This keeps core Kubernetes completely cloud-agnostic, allowing Kubernetes and cloud providers to evolve independently without creating hard dependencies.
    

## The Worker Plane (Worker Nodes)

- Worker nodes are managed entirely by the control plane.
    
- They contain all the necessary background services required to execute containerized applications.
    

## Worker Node Components

- **Pods:** The smallest deployable deployment entity in Kubernetes. A pod encapsulates one or more containers that share node resources and can communicate directly among themselves.
    
- **Kubelet:** The most critical component of a worker node. It communicates with the API server to receive pod specifications, ensures the pods and containers are running correctly, and continuously reports pod health and status back to the control plane.
    
- **Container Runtime:** The software responsible for downloading images and executing the containers. Kubernetes uses a Container Runtime Interface (CRI) for pluggability, allowing you to use runtimes like Docker, Podman, or CRI-O (transcribed as Creo).
    
- **Kubernetes Proxy (`kube-proxy`):** A network proxy running on every single node. It maintains the network rules that enable network communication to and from the pods running on that specific node.
    

## Quick Revision Questions


**1. What is the fundamental difference in responsibilities between the Control Plane and the Worker Plane?**

- The **Control Plane** acts as the "brain" of the cluster. It makes global decisions, monitors events, and manages the overall state of the system without running the actual applications.
    
- The **Worker Plane** (the worker nodes) consists of the actual machines (physical or virtual) that execute the workloads and run the user's containerized applications.
    

**2. Which control plane component acts as the single source of truth for the cluster's desired state and configuration?**

- **`etcd`**. It is a highly available, distributed key-value store that holds all the cluster's data and deployment configurations.
    

**3. How does the `kube-scheduler` decide where to place a newly created pod?**

- It selects the most optimal worker node by evaluating the node's available hardware resources, specific configuration options, and general Kubernetes scheduling principles.
    

**4. Why does Kubernetes utilize a separate Cloud Controller Manager instead of building cloud-specific features directly into the core code?**

- To keep the core Kubernetes system entirely **cloud-agnostic**. By separating cloud-specific logic into its own manager, Kubernetes and the various cloud providers (like AWS, Google Cloud, or Azure) can update and evolve their systems freely without breaking dependencies on each other.
    

**5. What is the primary role of the `kubelet` on a worker node?**

- The `kubelet` acts as the primary agent on each worker node. It communicates directly with the control plane's API server to receive pod specifications, ensures the containers are running as intended, and continuously reports the node's health and status back to the control plane.
    

**6. Which component is responsible for actually pulling the container images and running them, and what are three popular examples of this component?**

- The **Container Runtime**.
    
- Three commonly used runtimes are **Docker**, **Podman**, and **CRI-O**.
    

**7. What is the smallest deployable entity in Kubernetes, and what does it contain?**

- The **Pod**. It contains one or more tightly coupled containers that share the node's resources (like network and storage) and can communicate directly with each other.
