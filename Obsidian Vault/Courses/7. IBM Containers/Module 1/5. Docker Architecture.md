# Docker Architecture

## 1. Overview

Docker utilizes a **client-server architecture** to provide a complete, end-to-end application environment.

The architecture is built upon three primary components:

- **The Client**
    
- **The Host (Server)**
    
- **The Registry**
    

## 2. Core Components

### A. The Docker Client

- **Function:** The primary interface for users to interact with Docker.
    
- **Communication:** It uses the Docker Command Line Interface (CLI) or REST APIs to send instructions to the Docker Host.
    
- **Connectivity:** The client can communicate with a local Docker Host (running on the same system) or connect to a remote Docker Host.
    

### B. The Docker Host (Server)

- **The Daemon (`dockerd`):** The core background process running on the host server.
    
- **Function:** Listens for Docker API requests and processes commands (such as `docker build` or `docker run`).
    
- **The "Heavy Lifting":** The daemon is responsible for actually building, running, and distributing Docker containers.
    
- **Management:** The host securely manages various Docker objects, including:
    
    - Images
        
    - Containers
        
    - Namespace networks
        
    - Storage plugins and add-ons
        
- **Inter-daemon Communication:** Docker daemons can communicate with _other_ daemons to manage distributed Docker services.
    

### C. The Docker Registry

- **Function:** A centralized storage and distribution system for container images.
    
- **Public Registries:** Accessible by everyone (e.g., **Docker Hub**).
    
- **Private Registries:** Restricted access, highly preferred by enterprises for security reasons.
    
- **Hosting Options:** * Third-party cloud providers (e.g., IBM Cloud Container Registry).
    
    - Self-hosted inside private data centers or on private clouds.
        

## 3. The Containerization Process (Workflow)

The standard lifecycle of building, storing, and running a container using the Docker architecture follows these steps:

1. **Initialization:** Start with an existing base image or a `Dockerfile`.
    
2. **Build (`docker build`):** * The developer issues the build command.
    
    - The Docker Daemon creates a new container image and assigns it a name.
        
3. **Store/Push (`docker push`):** * Using automation or a build pipeline, the image is pushed to the Docker Registry for storage and future distribution.
    
4. **Run/Pull (`docker run`):**
    
    - A run command is issued (by a local machine, cloud system, or on-premises server) to create a running container from the image name.
        
    - **Local Check:** The Docker Host first checks if the requested image already exists locally.
        
    - **Pulling:** If the image is _not_ found locally, the Docker Client connects to the Registry and pulls (downloads) the image down to the Host.
        
    - **Execution:** Finally, the Docker Daemon uses that image to create and launch the running container.
