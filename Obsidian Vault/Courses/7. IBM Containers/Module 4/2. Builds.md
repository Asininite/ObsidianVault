## 1. What is a Build?

- **Definition:** A build is the process of transforming inputs into a resultant object (e.g., transforming source code into a runnable container image).
    
- **Build Configuration (BuildConfig):** A build fundamentally requires a `BuildConfig` file. This configuration file defines the _build strategy_ and the _input sources_ needed to execute the build.
    

### Anatomy of a BuildConfig File

A typical `BuildConfig` YAML file includes several key sections:

- **`runPolicy`:** Controls how builds run. Values include `default`, `serial` (sequentially), or `simultaneously`.
    
- **`triggers`:** Specifies a list of triggers that automatically kick off a new build.
    
- **`source` & `sourceType`:** Defines the primary input for the build (e.g., a Git repository, inline Dockerfile, or binary payloads).
    
- **`strategy`:** Specifies which strategy to execute (Source/S2I, Docker, or Custom).
    
- **`output`:** Defines the repository/registry where the newly built container image will be pushed.
    
- **`postCommit`:** Defines an optional build hook to run after the build completes.
    

## 2. Build Input Sources

A build input source provides the actual content for the builds. Multiple inputs can be combined into a single build.

**Order of Precedence:** If multiple inputs are provided, OpenShift prioritizes them in the following order (top to bottom):

1. **Inline Dockerfile definitions:** _Note: An inline Dockerfile takes ultimate precedence and will overwrite any external Dockerfile._
    
2. **Content extracted from existing images**
    
3. **Git repositories**
    
4. **Binary or local inputs**
    
5. **Input secrets**
    
6. **External artifacts**
    

## 3. Image Streams

- **Definition:** An abstraction used for referencing container images within OpenShift.
    
- **How they work:** An image stream continuously creates and updates container images, but **it does not contain the actual image data itself**. Instead, it serves as a pointer to images stored in internal/external registries or to other image streams.
    
- **Tags:** A single image stream can consist of many different tags (e.g., `latest`, `dev`, `test`). Each tag points to a specific image version in a registry.
    
- **Benefits:** * Rather than hardcoding a strict registry URL in your deployment, you refer to the image stream tag.
    
    - If the source image location changes, you simply update the image stream definition once, instead of manually updating all your individual deployments.
        
    - Provides trigger capabilities to automate builds/deployments when a new version of an image hits the stream.
        

## 4. Automating Builds (Build Triggers)

Rather than running builds manually, OpenShift allows you to automate the process using triggers.

1. **Webhook Triggers:** Sends a request to an API endpoint. This supports generic webhooks and widely used **GitHub webhooks** (which trigger a build automatically upon a new code commit, pull request, etc.).
    
2. **Image Change Triggers:** Triggers a build automatically when a new version of a base image becomes available (e.g., if you use a Node.js base image, your app will automatically rebuild when that base image receives security updates).
    
3. **Configuration Change Triggers:** Automatically causes a new build to run the moment you create a new `BuildConfig` resource.
    

## 5. Build Strategies

OpenShift utilizes three primary build strategies to convert inputs into container images:

### A. Source-to-Image (S2I) Strategy

- **How it works:** Injects your application source code into a pre-existing "builder image" to produce a ready-to-run container image.
    
- **Benefits:** It avoids the need to write a `Dockerfile` entirely. It enables going from raw source code to a running image in a single step. OpenShift comes with a variety of available builder images, saving massive development time.
    

### B. Docker Build Strategy

- **How it works:** Requires a repository that contains an actual `Dockerfile` and necessary artifacts. OpenShift takes the input, invokes the standard `docker build` command, creates the image, and pushes it to the internal OpenShift registry.
    
- **Implementation Methods:** 1. Replace Dockerfile from image
    
    2. Use Dockerfile path
    
    3. Use Docker environment variables
    
    4. Add Docker build arguments
    

### C. Custom Build Strategy

- **How it works:** You must define and create your own specific builder image. These are regular docker images that contain the specific, custom logic needed to transform inputs into expected outputs.
    
- **Capabilities:** While Docker and S2I strictly result in runnable images, custom builds can create additional objects like JAR files and execute CI/CD deployments that perform unit or integration tests.
    
- **Restriction:** Because they run with very high privileges, custom builds are **only available to cluster administrators**.
    

## Quick Revision Questions & Answers

**1. What is an Image Stream and does it actually store image data?**

- **Answer:** An Image Stream is an abstraction/pointer for referencing container images in OpenShift. No, it does not store the actual image data; it merely points to the images stored in registries.
    

**2. Which build input source takes the highest precedence and will overwrite external configurations?**

- **Answer:** Inline Dockerfile definitions.
    

**3. If you want a new build to trigger automatically every time a developer merges a pull request on GitHub, which trigger should you use?**

- **Answer:** A Webhook trigger (specifically, a GitHub webhook).
    

**4. What is the major advantage of using the Source-to-Image (S2I) build strategy?**

- **Answer:** It completely removes the need to write or manage a Dockerfile by automatically injecting your source code into a pre-configured builder image.
    

**5. Why are Custom Build Strategies restricted only to cluster administrators?**

- **Answer:** Because custom builds run with high system privileges and execute custom logic that could impact cluster security and stability.
