# Kubernetes Config Maps and Secrets

## 1. Best Practices: Configuration vs. Code

- **The Golden Rule:** As a software developer, you should always avoid hard-coding configuration variables directly into your application code.
    
- **The Goal:** Keep configuration variables completely separate. This ensures that any necessary changes to configuration settings do not require you to rewrite, rebuild, or redeploy your application code. Kubernetes achieves this separation using Config Maps and Secrets.
    

## 2. Config Maps

### A. Characteristics and Properties

- **Definition:** An API object that stores **non-confidential** data in key-value pairs.
    
- **Security:** It provides absolutely zero secrecy or encryption. It is strictly meant for non-sensitive information.
    
- **Size Limit:** Data stored inside a Config Map **cannot exceed 1 Megabyte (1MB)**. For larger amounts of data, you must consider mounting a persistent volume or using a separate database/file service.
    
- **Fields:** Unlike many other Kubernetes objects, a Config Map does _not_ have a `spec` field. Instead, it utilizes optional `data` and `binaryData` fields.
    
- **Naming:** The name of a Config Map must be a valid DNS subdomain name.
    
- **Reusability:** A single Config Map is highly reusable across multiple different deployments, effectively decoupling the environment configuration from the deployments themselves.
    

### B. Three Ways to Create a Config Map

1. **Using String Literals:** Providing the key-value pair directly in the command line (e.g., defining `message=hello` right in the terminal).
    
2. **Using a File or Directory:** Loading from an existing `.properties` or `key=value` file. This is highly useful for adding many variables at once instead of typing them one by one. If you specify a directory, Kubernetes loads the entire directory into the Config Map.
    
3. **Using a YAML Descriptor File:** Writing the configuration out in a standard Kubernetes YAML file and applying it to the cluster.
    

### C. Consuming a Config Map

Once created, Kubernetes applies the Config Map to the Pod or Deployment right before it runs. The application can consume this data in two main ways:

1. **As Environment Variables:** Using the `configMapKeyRef` attribute in the deployment YAML (e.g., Node.js code can then read it using `process.env.message`).
    
2. **As Volume Mounts:** Mounting the Config Map as a file inside the container using the volumes plugin.
    

## 3. Secrets

### A. Characteristics and Properties

- **Definition:** Operates very similarly to a Config Map, but is specifically designed to handle **sensitive and confidential information** (like passwords, OAuth tokens, and SSH keys).
    
- **Security:** When you view or describe a Secret (using `kubectl describe`), the display text masks the actual secret values. If viewed in YAML format, you will see that the value is fully encoded (typically base64) to protect it from being easily read in plain text.
    

### B. Creating and Consuming a Secret

The video outlines three primary ways Secrets are created and utilized by applications:

1. **Using a String Literal:** Creating the secret directly via the command line.
    
2. **Using Environment Variables:** Injecting the secret directly into the application's environment. The application code extracts it just like a regular variable (e.g., `process.env.API_CREDS`).
    
3. **Using Volume Mounts:** Mounting the secret as a physical file inside the container.
    
    - _Example:_ The secret `api-creds` is mounted as a file at the path `/etc/API`. The application is programmed to read and process that specific file to extract the hidden secret data safely.
        

## Quick Revision Questions & Answers

**1. Why is it a bad practice to hard-code configuration variables directly into your application's source code?**

- **Answer:** Because any future changes to those configuration settings would require you to edit the source code, rebuild the application image, and perform a full redeployment. Separating them allows you to update configs on the fly.
    

**2. What is the maximum data size limit for a single Kubernetes Config Map?**

- **Answer:** 1 Megabyte (1MB).
    

**3. If you need to pass highly sensitive database passwords to your application, should you use a Config Map?**

- **Answer:** No. Config Maps provide no encryption or secrecy. You should use a Kubernetes Secret instead.
    

**4. When looking at a Config Map's YAML descriptor, which standard Kubernetes field is noticeably missing?**

- **Answer:** The `spec` field. Config Maps use `data` and `binaryData` fields instead.
    

**5. What are the two primary ways a deployment or pod can "consume" (read) the data stored in a Config Map or Secret?**

- **Answer:** They can be injected as **Environment Variables** or mounted as physical files using **Volume Mounts**.
