# Kubernetes Rolling Updates

## 1. What is a Rolling Update?

- **Definition:** Automated updates that occur on a scheduled basis, rolling out app changes across pods in a controlled and automated way.
    
- **Compatibility:** They work closely with pod templates like Deployments.
    
- **Benefits:** They allow you to publish changes to applications without noticeable interruption (zero downtime) and provide a very easy mechanism to rollback if something goes wrong.
    

## 2. Preparation (Pre-steps for Rolling Updates)

Before enabling rolling updates, you must prepare your deployment properly to ensure traffic isn't routed to pods that aren't ready.

### A. Add Health Probes

- **Liveness and Readiness Probes:** You must add these probes to your deployments so the system knows exactly when the new pods are appropriately marked as "ready" to receive traffic.
    

### B. Configure the Strategy in YAML

You must define a rolling update strategy in your deployment's YAML configuration file using specific attributes to control how the rollout happens:

- **`maxSurge`:** Defines the maximum number of extra pods that can be added above your desired number of pods during the update.
    
    - _Example:_ If you have 10 pods, a `maxSurge` of 2 means the system will temporarily scale to a maximum of 12 pods during the update. Setting it to 100% would double the pods (create a complete replica) before taking the original set down.
        
- **`maxUnavailable`:** Defines the maximum number of pods that can be unavailable during the update process.
    
    - _Example:_ For a strict **zero-downtime** system, set `maxUnavailable` to `0`.
        
- **`minReadySeconds`:** An optional but useful attribute that forces Kubernetes to wait a specified number of seconds after a pod is ready before moving on to update the next pod in the rollout stage.
    

## 3. Executing a Rolling Update (Workflow)

Imagine you have an app displaying "Hello World!" running on 3 pods, and you need to update it to "Hello World v2" without downtime.

- **Step 1: Build and Push the New Image**
    
    - Outside of Kubernetes, you must use standard Docker commands to build, tag, and push the new version of your software to an image registry (like Docker Hub).
        
    - _Example tag:_ `hello-kubernetes:2.0`
        
- **Step 2: Apply the Update**
    
    - Use a command to set/change the image flag on your existing deployment to point to the new image tag.
        
- **Step 3: Monitor the Rollout**
    
    - Use the command `kubectl rollout status deployment/<deployment-name>` to monitor the deployment. The API will confirm when it has been successfully rolled out.
        

## 4. Rolling Back an Update

If there are errors in the new deployment or the client changes their mind, Kubernetes makes reverting extremely easy.

- **The Command:** Use the `undo` command on the rollout (e.g., `kubectl rollout undo deployment/<name>`).
    
- **The Process:** Use `kubectl get pods` to watch the process. You will see the new (v2) pods being terminated and brand new pods running the original (v1) version being created to replace them.
    

## 5. Rollout & Rollback Mechanisms

The video outlines two distinct ways these updates physically happen:

### A. All-at-Once (Causes Downtime)

- **Rollout:** All version 1 (v1) objects are completely removed _before_ version 2 (v2) objects can become active. User access is **blocked** (downtime) during the time lag between the v1 removal and v2 activation.
    
- **Rollback:** All v2 objects are completely removed before v1 objects become active. User access is similarly blocked.
    

### B. One-at-a-Time / Staggered (Zero Downtime)

- **Rollout:** The update is staggered. A new v2 pod is created. Once active, a single v1 pod is marked for deletion and removed. This one-by-one process repeats until all pods are replaced. User access is **not interrupted**.
    
- **Rollback:** The rollback is also staggered. A new v1 pod is created, and once ready, a v2 pod is deleted. This ensures seamless continuity for the users.
    

## Quick Revision Questions & Answers

**1. What two probes must be added to a deployment to properly prepare it for a rolling update?**

- **Answer:** Liveness probes and Readiness probes. (These ensure Kubernetes knows exactly when a new pod is truly ready to handle user traffic).
    

**2. If you want to absolutely guarantee zero downtime during a rolling update, what must the `maxUnavailable` attribute be set to?**

- **Answer:** `0`.
    

**3. What does the `maxSurge` attribute control during a rolling update?**

- **Answer:** It dictates the maximum number of extra pods that can be temporarily created above the desired replica count during the update process. (e.g., A max surge of 100% means temporarily doubling the number of pods).
    

**4. How do you revert a deployment to its previous version if an update fails or is rejected?**

- **Answer:** You perform a rollback by using the `undo` command on the rollout.
    

**5. What is the critical disadvantage of an "all-at-once" rollout strategy compared to a "one-at-a-time" staggered strategy?**

- **Answer:** An all-at-once strategy removes all old pods before spinning up the new ones, completely blocking user access and causing downtime. A one-at-a-time strategy staggers the replacement so user access is never interrupted.
