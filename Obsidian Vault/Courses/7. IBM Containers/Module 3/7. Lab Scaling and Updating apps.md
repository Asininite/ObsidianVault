# Kubernetes: Scaling, Updating, and Configuring Applications

## 1. Overview and Objectives

This lab focuses on the practical management of application lifecycles in Kubernetes. It covers four critical operational tasks:

1. **Manual Scaling:** Using a ReplicaSet to scale an application up and down.
    
2. **Rolling Updates & Rollbacks:** Safely updating application code with zero downtime and reverting if necessary.
    
3. **ConfigMaps:** Decoupling application configuration from the codebase.
    
4. **Autoscaling:** Using the Horizontal Pod Autoscaler (HPA) to dynamically scale based on load.
    

## 2. Environment Setup and Initial Deployment

Before scaling or updating, an application must be built, pushed to a registry, and deployed to the Kubernetes cluster.

### A. Building and Pushing the Image

- **Command:** `docker build -t <registry_url>/<namespace>/<app_name>:<tag> .`
    
- **Command:** `docker push <registry_url>/<namespace>/<app_name>:<tag>`
    
- _Example in Lab:_ `docker build -t us.icr.io/$MY_NAMESPACE/hello-world:1 . && docker push us.icr.io/$MY_NAMESPACE/hello-world:1`
    

### B. Deploying and Exposing the App

- **Deploying:** Apply the configuration file using `kubectl apply -f deployment.yaml`.
    
- **Verification:** Ensure pods are running using `kubectl get pods`.
    
- **Exposing (Service):** To access the application, it must be exposed.
    
    - **Command:** `kubectl expose deployment/hello-world`
        
    - _Note:_ By default, this creates a **ClusterIP** service, which is only accessible from _inside_ the cluster.
        
- **Local Access (Proxy):** For lab and development purposes, running `kubectl proxy` creates a local gateway that allows you to securely access the internal ClusterIP service from your local machine.
    

## 3. Manual Scaling (ReplicaSets)

Load on an application varies. You can manually adjust the number of running instances to accommodate this load.

- **Scaling Up:**
    
    - **Command:** `kubectl scale deployment <deployment-name> --replicas=<number>`
        
    - _Example:_ `kubectl scale deployment hello-world --replicas=3`
        
- **Verifying Load Balancing:** By querying the application multiple times (e.g., using a `curl` loop), you will observe that the responses come from different pods, proving that Kubernetes is actively load-balancing traffic across all replicas.
    
- **Scaling Down:** Simply run the exact same `scale` command with a lower `--replicas` count (e.g., `--replicas=1`). Kubernetes will gracefully terminate the excess pods.
    

## 4. Performing Rolling Updates and Rollbacks

Rolling updates allow you to update an application to a new version in an automated, staggered fashion, preventing downtime.

### A. The Rollout Process

1. **Modify and Build:** Change the application code (e.g., updating a welcome message in `app.js`) and build a new image with a **new tag** (e.g., `hello-world:2`).
    
2. **Set New Image:** Instruct the deployment to use the new image version.
    
    - **Command:** `kubectl set image deployment/hello-world hello-world=us.icr.io/$MY_NAMESPACE/hello-world:2`
        
3. **Monitor the Rollout:** Check the real-time status of the update.
    
    - **Command:** `kubectl rollout status deployment/hello-world`
        
4. **Verify:** Use `kubectl get deployments -o wide` to confirm the `IMAGES` column now reflects the new tag (v2).
    

### B. The Rollback Process (Undoing an Update)

If a bug is discovered in the new version, Kubernetes allows for an instant rollback to the previous stable state.

- **Command:** `kubectl rollout undo deployment/hello-world`
    
- After running this, the deployment immediately scales down the buggy v2 pods and spins up the v1 pods.
    

## 5. Using ConfigMaps for Application Configuration

**Best Practice:** Configuration data should never be hardcoded into the application code. It should be passed in externally.

### A. Creating and Applying a ConfigMap

1. **Create from Literal:** Create the ConfigMap directly from the command line.
    
    - **Command:** `kubectl create configmap app-config --from-literal=MESSAGE="This message came from a ConfigMap!"`
        
2. **Mounting as Environment Variables:** In the `deployment.yaml`, you reference the ConfigMap so its data is injected into the container as environment variables:
    
    ```
    envFrom:
      - configMapRef:
          name: app-config
    ```
    
3. **Application Code:** The application is updated to read the variable (e.g., in Node.js: `process.env.MESSAGE`).
    
4. **Deploy:** Build the new image (v3) and apply the updated deployment YAML.
    

### B. Updating a ConfigMap (Without Rebuilding the Image)

The true power of ConfigMaps is the ability to change app behavior _without_ rewriting code or rebuilding Docker images.

1. **Update the ConfigMap:** Delete the old one and recreate it with a new message.
    
2. **Restart the Deployment:** Because environment variables are only injected when a container _starts_, **you must restart the pods** for the new ConfigMap values to take effect.
    
    - **Command:** `kubectl rollout restart deployment hello-world`
        

## 6. Autoscaling with Horizontal Pod Autoscaler (HPA)

Instead of manually scaling with `kubectl scale`, HPA automatically increases or decreases replicas based on actual resource utilization.

### A. The Prerequisite: Resource Limits

For HPA to work, **it must be able to calculate metrics**. Therefore, you _must_ define CPU/Memory requests and limits inside your `deployment.yaml` under the container spec:

```
resources:
  limits:
    cpu: 50m
  requests:
    cpu: 20m
```

### B. Implementing HPA

1. **Create the Autoscaler:** Use the CLI to set the metric thresholds and limits.
    
    - **Command:** `kubectl autoscale deployment hello-world --cpu-percent=5 --min=1 --max=10`
        
    - _Explanation:_ If average CPU usage across pods exceeds 5%, Kubernetes will add more pods (up to a maximum of 10). If it drops, it scales back down (to a minimum of 1).
        
2. **Monitor HPA:** Use `kubectl get hpa hello-world`.
    
3. **Test Under Load:** If you artificially generate massive traffic (e.g., curling the app 100,000 times), you can run `kubectl get hpa hello-world --watch` and see the `REPLICAS` count dynamically increase to handle the spike in traffic.
    

## Quick Revision Questions & Answers

**1. What is the difference between `kubectl scale` and `kubectl autoscale`?**

- **Answer:** `kubectl scale` requires manual intervention to hardcode a specific number of desired replicas. `kubectl autoscale` creates an HPA object that dynamically adjusts the number of replicas based on real-time metrics (like CPU usage) within a defined minimum and maximum range.
    

**2. Why must you run `kubectl rollout restart deployment` after updating a ConfigMap?**

- **Answer:** When ConfigMap values are injected as environment variables, they are only read during the initial startup of the container. Restarting the deployment forces the old pods to terminate and new pods to start, loading the updated configuration values.
    

**3. What critical configuration must be added to a `deployment.yaml` before a Horizontal Pod Autoscaler (HPA) can function properly?**

- **Answer:** You must define **resource requests and limits** (e.g., CPU limits) for the containers. Without these baselines, HPA cannot calculate the utilization percentages required to trigger scaling actions.
    

**4. What command is used to quickly revert a deployment to its previous version?**

- **Answer:** `kubectl rollout undo deployment/<deployment-name>`
    

**5. What is the purpose of the `kubectl proxy` command used in this lab?**

- **Answer:** Because the application was exposed using a `ClusterIP` service (which is only accessible from inside the Kubernetes cluster), `kubectl proxy` creates a secure gateway that routes traffic from your local machine's browser/terminal into the cluster to access the service.
