# Kubernetes Service Binding

## 1. What is Service Binding?

- **Definition:** Service binding is the process required to easily consume external or "backing" services (such as REST APIs, databases, and event buses) within your Kubernetes applications.
    
- **Core Purpose:** It manages the configuration and credentials for backend services while securely protecting sensitive data.
    
- **The Mechanism:** It automatically makes the required service credentials available to your cluster by converting them into a **Kubernetes Secret**. The application code then uses these credentials from the binding to seamlessly call the corresponding external service.
    

## 2. Steps to Bind a Service (IBM Cloud Example)

The video uses the IBM Watson Tone Analyzer service to demonstrate how to bind an external cloud service to a Kubernetes cluster. The workflow involves four main steps:

### Step 1: Provision an Instance

- You must first provision a live instance of the external service.
    
- This can be done using the Command Line Interface (CLI) or through the cloud provider's web catalog (e.g., the IBM Cloud website).
    

### Step 2: Bind the Service to the Cluster

- Use the service bind command to connect the newly created service instance to your Kubernetes cluster.
    
- **What happens in the background:** The cloud service binding automatically creates a Kubernetes Secret containing the service credentials.
    
- **Format:** These credentials are **base64 encoded** and securely stored inside the Secret in **JSON format**.
    

### Step 3: Verify the Secret

- Once bound, you can verify that the secret exists in your cluster.
    
- **CLI Method:** Run the `get secrets` command (e.g., `kubectl get secrets`) to see all secrets in the cluster.
    
- **UI Method:** You can also view the secrets through the Kubernetes dashboard User Interface or your cloud provider's console.
    

### Step 4: Configure the App to Access the Secret

To actually use the data in the Secret, your application needs a way to read it. There are two primary options for this:

#### Option A: Volume Mounts

- You can mount the Secret as a volume directly to your Pod.
    
- **Result:** This action creates a physical, JSON-formatted file named `binding` stored in the designated Volume Mounts directory inside the container.
    
- The application can then read this file to extract all the information and credentials required to access the service.
    

#### Option B: Environment Variables

- You can reference the Secret directly as environment variables in the pod configuration.
    
- **Result:** The credentials are injected into the application's runtime environment.
    
- _Example:_ Variables like `binding.apikey`, `binding.username`, and `binding.password` are injected. A Node.js application can then easily consume them using code like `process.env.binding_API_Key`.
    

## Quick Revision Questions & Answers

**1. What is the primary goal of Service Binding in Kubernetes?**

- **Answer:** To securely manage configuration and credentials for external backing services (like databases or APIs) so that applications can easily consume them without exposing sensitive data.
    

**2. When you bind an external service to a Kubernetes cluster, what native Kubernetes object is automatically created to store the credentials?**

- **Answer:** A Kubernetes Secret.
    

**3. In what format are the service credentials stored inside the Kubernetes Secret?**

- **Answer:** They are base64 encoded and stored in JSON format.
    

**4. What are the two primary ways an application can access the credentials stored in the binding Secret?**

- **Answer:** By mounting the Secret as a **Volume** (which creates a JSON file) or by referencing the Secret as **Environment Variables**.
    

**5. If you choose to mount the service binding Secret as a volume, what is the default name of the JSON-formatted file created in the container?**

- **Answer:** It creates a file named `binding`.
