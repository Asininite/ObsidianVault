# Practical Kubernetes: Lab Breakdown & Concepts

This guide walks through your practice lab step-by-step. Instead of just showing the commands, we will break down the "Why" and the "How" behind each Kubernetes object you created, filling in the crucial technical details found inside the YAML files.

## Phase 1: Containerizing the Application (The Dockerfile)

**What we did:** We looked at a `Dockerfile`, built an image (`docker build`), and pushed it to the IBM Cloud Container Registry (`docker push`).

**The Concept:** Kubernetes is a **[[!1. Container]] orchestrator**. It doesn't run raw source code; it runs containers. Before Kubernetes can do its job, your application must be packaged into a static, portable container image.

**Deep Dive: The Dockerfile Instructions**

- `FROM node:14`: Every image starts with a base. This pulls a pre-configured Linux environment with Node.js version 14 already installed.
    
- `WORKDIR /app`: Sets the default directory inside the container. Subsequent commands run from here.
    
- `COPY ...`: Moves your source code from your local machine into the container's file system.
    
- `EXPOSE 3000`: A documentation instruction telling Docker/Kubernetes that this container listens on port 3000.
    
- `CMD ["node", "main.js"]`: The default command that executes when the container finally starts up.
    

**The "Why" & The Benefit:**

- **Why we do it:** We are giving Kubernetes a standard package that contains _everything_ our app needs to run. By pushing it to a Registry (like IBM Cloud CR), we make that image globally available to any node in our cluster.
    
- **The Benefit:** "It works on my machine" syndrome is cured. Because the image contains its own environment, Kubernetes can pull this exact image onto any server in the world, and it will run identically.
    

## Phase 2: Deploying the App (Deployments & Pods)

**What we did:** We applied a `deployment.yml` file to the cluster and used `kubectl port-forward` to view the app.

**The Concept:**

A Deployment is the manager of your application. You never deploy a "naked" Pod because Pods are mortal (if a Pod dies, it stays dead). A Deployment ensures self-healing and zero-downtime rolling updates.

**Deep Dive: The YAML Anatomy & The "Glue" of Kubernetes**

If you look closely at the `deployment.yml`, you'll notice a `selector` block and a `template.metadata.labels` block.

- **Labels and Selectors:** This is how Kubernetes objects talk to each other. The Deployment doesn't "own" the pods; instead, the Deployment's `selector` constantly looks for any Pods that have the matching label (`app: myapp`).
    
- **ImagePullPolicy: Always:** This instruction in the YAML forces the node to pull a fresh copy of your image from the registry every time the pod starts, ensuring you aren't running a stale, cached version.
    
- **Resources:** We defined CPU `limits` (maximum allowed) and `requests` (minimum guaranteed). This tells the Kubernetes Scheduler exactly how much compute power this app needs, so the scheduler can pick the best physical Node to host it.
    

**The Benefit:** Self-healing and dynamic scheduling. The `RollingUpdate` strategy means that when you release `v2` of your app, Kubernetes will start the new version _before_ killing the old version, ensuring your users never see a "Site Offline" page.

## Phase 3: Decoupling Configuration (ConfigMaps)

**What we did:** We ran `kubectl create configmap myapp-config --from-literal=server-url=http://example.com` to create variables for our app.

**The Concept:**

A ConfigMap is an API object used to store non-confidential data in key-value pairs.

**Deep Dive: Imperative vs. Declarative**

We used the `--from-literal` flag in the CLI. This is an _imperative_ command (telling Kubernetes exactly what to do right now in the terminal), as opposed to creating a YAML file (which is _declarative_). It allows you to rapidly inject environment variables into your cluster.

**The "Why" & The Benefit:**

- **Why we do it:** If your database IP changes and you hardcoded it into your app, you would have to edit the code, rebuild the Docker image, and redeploy everything.
    
- **The Benefit:** ConfigMaps decouple configuration from code. Your Docker image remains exactly the same across Dev, Staging, and Production environments—you just swap out the ConfigMap in each environment.
    

## Phase 4: Ensuring Cluster-Wide Availability (DaemonSets)

**What we did:** We applied a `daemonset.yaml` file.

**The Concept:**

A standard _Deployment_ says "I want X copies of my app running _somewhere_ in the cluster." A _DaemonSet_ says "I want exactly 1 copy of this app running on _every single server (Node)_ in the cluster."

**Deep Dive: Taints and Tolerations**

The lab's YAML included a specific block:

```
tolerations:
  - key: node-role.kubernetes.io/master
    effect: NoSchedule
```

- **Taints:** By default, Kubernetes places a "Taint" on the Master Node (Control Plane) that says `NoSchedule`. This acts like a repellent, preventing standard application pods from running on the Master Node so it doesn't get overwhelmed.
    
- **Tolerations:** The block in our YAML is a "Toleration." It gives our DaemonSet a special exception to ignore that repellent. Because DaemonSets are often used for cluster-wide logging or monitoring, they _need_ to run on every node, including the Master Node.
    

**The Benefit:** DaemonSets are perfect for background infrastructure tasks. When you add a new physical server to your cluster, the DaemonSet automatically detects it and provisions your logging/monitoring pod onto it without manual intervention.

## Phase 5: Stable Networking (Services)

**What we did:** We applied a `service.yaml` file with the type `NodePort`.

**The Concept:**

Pods are ephemeral (they die and are recreated constantly). Every time a Pod is recreated, it gets a **brand new IP address**. A Kubernetes Service provides a single, permanent IP address and DNS name that acts as a stable load balancer sitting in front of your Pods.

**Deep Dive: The Port Mapping Puzzle**

In the `service.yaml`, there are three distinct ports happening:

- `targetPort: 3000`: This is the port your actual container is listening on (matching the `EXPOSE 3000` in the Dockerfile).
    
- `port: 80`: This is the internal port of the Service itself. Other apps _inside_ the cluster can reach this app via this standard HTTP port.
    
- `type: NodePort`: Because ClusterIPs are only accessible internally, `NodePort` tells Kubernetes to open a port (usually in the 30000-32767 range) on the physical host machines so external traffic from the internet can reach the Service.
    

**The Benefit:** Reliable communication. The Service watches for Pods with the label `app: myapp`. When a new Pod is created, the Service automatically routes traffic to it, abstracting away the chaotic lifecycle of the underlying pods.

## Phase 6: Securing Sensitive Data (Secrets)

**What we did:** We created a Secret using `kubectl create secret generic`, passing in a username and password.

**The Concept:**

A Secret is like a ConfigMap, but designed to hold sensitive data (passwords, tokens).

**Deep Dive: The "Opaque" Generic Secret**

When we ran `kubectl get secret`, the type was listed as **Opaque** (Generic). This simply means Kubernetes treats the data as an arbitrary base64-encoded key-value pair and doesn't apply any special validation to it. (Other types include `kubernetes.io/tls` for SSL certificates or `kubernetes.io/dockerconfigjson` for private registry passwords).

**The Benefit:** Security. You should absolutely never put passwords in your source code, your Dockerfile, or a standard ConfigMap. Secrets allow you to restrict who can view sensitive data via RBAC (Role-Based Access Control) and pass them securely to Pods at runtime.

## Phase 7: Persisting Data (PVs and PVCs)

**What we did:** We looked at a YAML file that created both a PersistentVolume (PV) and a PersistentVolumeClaim (PVC).

**The Concept:**

By default, the storage inside a container is temporary. If a database Pod crashes, all data saved inside it is permanently deleted.

- **PV (Persistent Volume):** Actual storage infrastructure in the cluster provisioned by an administrator.
    
- **PVC (Persistent Volume Claim):** A "ticket" created by a developer requesting a specific amount of storage (e.g., 1Gi).
    

**Deep Dive: Access Modes & HostPaths**

- `hostPath`: Used in the PV YAML, this tells Kubernetes to use a directory on the physical Node's local hard drive (`/data`). _Note: This is mostly for single-node testing. In production, you would use cloud storage like AWS EBS or NFS, because if a pod moves to a different node, it loses access to that local `hostPath`._
    
- `ReadWriteOnce (RWO)`: This Access Mode means the volume can only be mounted as read-write by a **single Node** at a time. It prevents data corruption that could happen if two nodes tried to write to the exact same file simultaneously.
    

**The Benefit:**

It creates a clean separation of duties. Developers don't need to know _how_ the cloud provider's storage works; they just write a PVC asking for "1 Gigabyte of space", and Kubernetes binds that claim to an available PV in the background, ensuring data survives pod crashes.
