### **Topic 1: Issues in Failure Recovery**

**Q: Discuss the major issues and challenges involved in failure recovery in distributed systems. [Part B, 14 Marks]**

**Answer:** Recovering from a failure in a distributed system is highly complex because processes do not share physical memory or a global clock. The major issues in failure recovery include:

**1. Domino Effect (Cascading Rollbacks)** This is the most severe issue in uncoordinated recovery systems. If Process A rolls back to an earlier state, it might force Process B to roll back to maintain consistency. Process B's rollback might then force Process C to roll back. This chain reaction can cascade out of control, potentially forcing the entire system to roll back to the absolute beginning of the program, completely defeating the purpose of saving checkpoints.

**2. Orphan Processes and Messages** An orphan message is created when a process rolls back to an earlier checkpoint, effectively "undoing" the sending of a message, but the receiving process has already received and processed it. The receiving process is now an "orphan process" because its current state depends on a message that mathematically never existed. The system must force the orphan process to roll back to resolve this paradox.

**3. Lost Messages** A lost message occurs when a receiving process crashes and rolls back to a state _before_ it received a message. However, the sender process did not crash, so its state still records that the message was successfully sent. Because the sender thinks the transmission is complete, it will not resend the message, and the data is permanently lost in the network.

**4. Duplicate Messages** When a sender process rolls back to a checkpoint, it will naturally re-execute its code and re-send its messages. If the receiving process _did not_ roll back, it will receive the exact same message a second time. The underlying recovery protocol must have mechanisms (like message sequence numbers) to detect and discard these duplicate messages so they don't corrupt the receiver's state.

**5. Recovery Overhead** The act of recovering from a failure consumes massive system resources. The overhead includes the time taken to detect the crash, the network bandwidth used to broadcast recovery messages, the computational power required to search for a consistent global state, and the disk I/O time required to reload checkpoints and replay message logs. During this time, normal application execution is halted.

**6. Maintaining Consistency** The primary goal of any recovery algorithm is to restore the system to a **Consistent Global State**. This means ensuring that the restored timeline is logically possible (i.e., no orphan messages). Designing algorithms that can mathematically guarantee this consistency across a chaotic network is a major structural challenge.

**7. Synchronization During Recovery** When a crash happens, you cannot simply restart the failed process in isolation. The system must synchronize all surviving processes. They must all temporarily pause their normal execution, communicate over the network to agree on which checkpoints form a valid recovery line, flush their communication channels, and then synchronously resume execution together.

### **Topic 2: Three Classifications of Checkpointing**

**Q: Explain the three classifications of checkpoint-based rollback recovery. [Part B, 8 Marks]**

**Answer:** To deal with the issues mentioned above (especially the domino effect), systems use different checkpointing strategies:

**1. Uncoordinated Checkpointing**

- **Concept:** Every process decides when to take its own checkpoints completely independently, without any network synchronization.
    
- **Impact:** It has very low overhead during normal execution, but it is highly susceptible to the **Domino Effect**. Recovery is slow and complex because the system has to search through many old checkpoints to find a consistent state.
    

**2. Coordinated Checkpointing**

- **Concept:** Processes communicate over the network to coordinate their actions. They temporarily pause execution and take their checkpoints at the exact same logical time to ensure they form a perfect, mathematically consistent global state.
    
- **Impact:** It completely eliminates the Domino Effect and makes recovery extremely fast. However, it introduces significant network overhead and pauses during normal execution.
    

**3. Communication-Induced Checkpointing (CIC)**

- **Concept:** A hybrid approach. Processes take independent checkpoints, but they also piggyback protocol metadata onto every application message they send. If a receiving process detects a dangerous communication pattern in this metadata that _might_ cause a domino effect later, it is **forced** to take an emergency checkpoint before reading the message.
    
- **Impact:** It prevents the domino effect without needing the heavy global synchronization messages of coordinated checkpointing.
