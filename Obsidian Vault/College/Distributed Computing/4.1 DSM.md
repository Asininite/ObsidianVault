- abstraction provided to programmer 
- gives impression of single monolithic memory
- programmers access data using traditional read write primitives
- do not deal with send receive primitives and complexity

### Advantages:

**1. Simpler Programming Model**  
DSM hides the complexity of message passing. Programmers use conventional **read and write operations** instead of explicit **send() and receive() primitives**, making distributed programming easier.

**2. Single Address Space Abstraction**  
DSM provides the impression of a **single monolithic memory**, even though memory is physically distributed across multiple machines.

**3. Massive Virtual Memory Space**  
By combining the memory of multiple nodes, DSM can provide a much larger virtual memory space than a single machine.

**4. Data Access Transparency**  
Processes can access data without knowing where it is physically located. This provides location transparency.

**5. Simplifies Complex Data Structures**  
Complex structures such as linked lists, trees, and graphs can be accessed naturally using references, unlike message-passing systems where structures must be packed and transmitted.

**6. Exploits Locality of Reference**  
Frequently accessed data can be cached locally, improving performance.

**7. No Single Memory Bottleneck**  
Unlike centralized shared memory systems, DSM avoids a single shared bus or centralized memory bottleneck.

**8. Cost Effective**  
DSM can be implemented using ordinary off-the-shelf computers connected by a network, making it cheaper than specialized multiprocessor systems.

**9. Portability**  
DSM programs can be portable because they use a common programming interface independent of specific hardware.

---

## Disadvantages / Issues in Implementing Distributed Shared Memory

Although DSM simplifies programming, it introduces several implementation challenges.

### Disadvantages:

**1. Performance Overhead**  
Accessing remote memory requires network communication, which is much slower than local memory access.

**2. Complex Consistency Management**  
Maintaining consistency among multiple cached copies of data across nodes is difficult and requires complex coherence protocols.

**3. False Sharing**  
When different processes update different variables located in the same memory block, unnecessary coherence traffic may occur.

**4. Thrashing**  
If multiple nodes repeatedly modify the same shared data, the memory block may continuously move between nodes, causing severe performance degradation.

**5. Synchronization Overhead**  
Locks, coordination, and synchronization mechanisms add communication overhead.

**6. Scalability Limitations**  
As the number of nodes increases, maintaining coherence and consistency becomes increasingly difficult.

**7. Complex Coherence Protocols**  
Implementing protocols to maintain correct shared memory semantics is challenging.

**8. Fault Tolerance Issues**  
Node failures may affect data availability and consistency.

**9. Programmer Awareness for Performance**  
Although DSM hides complexity, programmers must still understand data placement and access patterns to avoid poor performance.


## Design Issues

These are talking specifically about **DSM design decisions related to shared data semantics and replication**, not the broader DSM issues list.

## 1. Determining what semantics to allow for concurrent access to shared objects

This means:

**If multiple processes access the same shared data at the same time, what rules should govern that access?**

That rule set is called **semantics**.

### Example:

Suppose P1 and P2 both access variable X.

- P1 writes:
    

```text
X = 10
```

- P2 reads X.
    

Question:

**Should P2 immediately see 10?**  
**Can it still see the old value?**  
**What happens if both write at once?**

These rules must be defined.

That is deciding **memory access semantics** (consistency model).

Examples:

- Sequential consistency
    
- Weak consistency
    
- Causal consistency
    

### Why important?

Because programmers need to know the rules before writing correct programs.

That is what this means:

> “Semantics needs to be clearly specified so programmer can code appropriately.”

---

## 2. Determining how to implement those semantics

Once you decide the rules—

**How do you enforce them?**

That is the implementation problem.

One major method:

## Replication

Store copies of shared data at multiple nodes.

---

### Option A: Partial Replication

Only some nodes hold copies.

Example:

```text
Node A → has copy
Node B → has copy
Node C → no copy
```

Less overhead.

---

### Option B: Full Replication

Every node has a copy.

```text
A → copy
B → copy
C → copy
D → copy
```

Faster reads.

But updates become harder.

---

## Another decision:

How to replicate?

### Read Replication

Replicate mainly to speed up reads.

Good when:

- many reads
    
- few writes
    

---

### Write Replication

Replicate updates everywhere when writes occur.

Harder but keeps copies consistent.

---

So this bullet means:

**Once you choose the semantics, decide what replication strategy will enforce them.**

---

## 3. Selecting locations for replication

Now suppose you use partial replication.

Question:

**Where should copies be placed?**

That is replica placement.

---

### Example

Suppose:

- Users in Kerala access file heavily.
    

It makes sense to place a replica in Kochi.

Not Delhi.

That improves:

- Access speed
    
- Less network traffic
    
- Better efficiency
    

---

## This is basically:

**Where should copies live?**

That is the design issue.

---

## In simple terms, these 3 mean:

### First decide:

**What rules should shared access follow?**  
(semantics)

---

### Then decide:

**How will I enforce those rules?**  
(replication strategy)

---

### Then decide:

**Where should replicas be placed?**  
(replica location)

---

That is the flow. They are really three sequential design decisions.
