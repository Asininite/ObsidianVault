To assess and evaluate a programming language, we use a specific set of metrics. These criteria help us understand why one language might be chosen over another for a specific project. For your exams, you should focus on the four primary criteria: **Readability, Writability, Reliability, and Cost**.

Here is a detailed breakdown of each criterion and the characteristics that affect them.

---

### 1. Readability

Readability is the ease with which programs can be read and understood. It is widely considered one of the most important criteria for judging a programming language. If a program is unnatural and convoluted, it becomes unusually difficult to read and maintain.

Readability is influenced by several characteristics:

- **Overall Simplicity:** A language with a large number of basic constructs is more difficult to learn than one with a smaller number. Readability is harmed by **feature multiplicity** (having more than one way to accomplish a particular operation, such as `count = count + 1`, `count += 1`, `count++`, `++count`). Another problem is **operator overloading**, where a single operator symbol has more than one meaning.
    
- **Orthogonality:** This means that a relatively small set of primitive constructs can be combined in a relatively small number of ways to build the control and data structures of the language. A highly orthogonal language has fewer exceptions to its rules, which means a higher degree of regularity in the design, making it easier to read and understand.
    
- **Data Types:** The presence of adequate facilities for defining data types and data structures is a significant aid to readability. For example, using a Boolean type (`timeOut = true`) is perfectly clear, whereas using a numeric type for an indicator flag (`timeOut = 1`) makes the statement's meaning unclear.
    
- **Syntax Design:** This includes the forms of a language's special words (like `while`, `class`, and `for`) and how statement groups are formed. For instance, Ada uses distinct closing syntax like `end if` and `end loop`, which makes the code clearer than just using generic braces. Furthermore, semantics (meaning) should follow directly from syntax (form).
    

### 2. Writability

Writability is a measure of how easily a language can be used to create programs for a chosen problem domain. Most of the language characteristics that affect readability (like simplicity and orthogonality) also affect writability.

Key characteristics unique to writability include:

- **Support for Abstraction:** Abstraction is the ability to define and use complicated structures or operations in ways that allow many of the details to be ignored. Languages can support **process abstraction** (e.g., using a subprogram to implement a sort algorithm) and **data abstraction** (e.g., creating a binary tree class that hides its pointer implementation).
    
- **Expressivity:** This means a language has relatively convenient, rather than cumbersome, ways of specifying computations. For example, in C, the notation `count++` is more convenient and shorter than writing `count = count + 1`.
    

### 3. Reliability

A program is considered reliable if it performs to its specifications under all conditions. Interestingly, both readability and writability heavily influence reliability; programs that are difficult to read are difficult to write and modify without creating bugs.

Characteristics that ensure reliability:

- **Type Checking:** This is the process of testing for type errors in a given program, either by the compiler or during program execution. Because run-time type checking is expensive, compile-time type checking is more desirable. The earlier errors are detected, the less expensive it is to fix them.
    
- **Exception Handling:** This is the ability of a program to intercept run-time errors (and other unusual conditions), take corrective measures, and then continue execution.
    
- **Restricted Aliasing:** Aliasing is a dangerous feature where two or more distinct names (like two pointers) can be used to access the same memory location. Changing the value via one pointer silently changes the value referenced by the other, which can lead to severe reliability issues.
    

### 4. Cost

The total cost of a programming language is a function of many of its characteristics. When evaluating a language for a project, organizations must consider:

- The cost of **training** programmers to use the language.
    
- The cost of **writing** programs in the language.
    
- The cost of **compiling** programs.
    
- The cost of **executing** programs (execution speed is greatly influenced by language design).
    
- The cost of the **language implementation system**.
    
- The cost associated with **poor reliability** (e.g., system failures or bugs).
    
- The cost of **maintaining** programs, which includes corrections and modifications to add new functionality.
    

### Additional Minor Criteria

While the four above are the most critical, a few other criteria are sometimes used to evaluate languages:

- **Portability:** The ease with which programs can be moved from one implementation (or machine) to another.
    
- **Generality:** The applicability of the language to a wide range of applications.
    
- **Well-definedness:** The completeness and precision of the language's official defining document.

### **1. Reliability vs. Cost of Execution**

This is a classic conflict between safety and performance.

- **The Core Conflict:** We want languages to be highly reliable (meaning they catch errors before they cause a system crash), but enforcing that reliability usually requires the compiler or interpreter to do extra checks while the program is running. These extra checks consume CPU cycles and memory, thereby increasing the cost of execution.
    
- **The KTU Exam Example:** **Java's Array Index Checking.** * In Java, the language guarantees that every time you try to access an element in an array, it checks if your index is within the valid bounds.
    
    - **The Benefit (Reliability):** This prevents catastrophic memory access errors and buffer overflows, making the program highly reliable.
        
    - **The Trade-off (Cost):** Checking the index boundary on _every single array access_ slows down the execution speed of the program, increasing the overall cost of execution. (In contrast, C does not do this check, making it faster but less reliable).
        

---

### **2. Readability vs. Writability**

This is the conflict between making a language easy to author quickly versus making it easy to understand later.

- **The Core Conflict:** We want languages to be expressive so programmers can write complex logic quickly and compactly (Writability). However, if a language provides too many shortcuts, weird symbols, or highly dense operators to achieve this, the resulting code becomes incredibly difficult for someone else (or even the original author six months later) to read and maintain (Readability).
    
- **The KTU Exam Example:** **The APL Programming Language.**
    
    - APL is a language designed with a massive set of powerful, custom operators and new symbols.
        
    - **The Benefit (Writability):** A programmer can write a highly complex matrix operation in just one or two extremely compact lines of code.
        
    - **The Trade-off (Readability):** Because it uses so many unique symbols and packs so much logic into a tiny space, the code looks like an unreadable string of hieroglyphics to anyone who isn't a master of the language, resulting in notoriously poor readability.

- **The Core Conflict:** Giving a programmer massive flexibility to manipulate the system makes writing code easier and more powerful, but it dramatically increases the chances of them making a fatal error.
    
- **The KTU Exam Example:** **C++ Pointers.**
    
    - **The Benefit (Writability/Flexibility):** C++ allows programmers to use pointers to directly manipulate memory addresses. This is a very powerful and flexible tool for writing efficient systems code.
        
    - **The Trade-off (Reliability):** Because pointers are so flexible, they are notorious for being used incorrectly (like dangling pointers or memory leaks), making the language inherently less reliable.
