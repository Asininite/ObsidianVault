# 2. HTTP Security Fundamentals

HTTP itself is:

- **Stateless**
    
- **Plaintext**
    
- **Vulnerable to eavesdropping, tampering, and impersonation**
    

Therefore security requires:

1. **Encryption** (TLS/SSL → HTTPS)
    
2. **Authentication** (passwords, tokens, certificates)
    
3. **Integrity** (server assures content isn't modified)
    
4. **Confidentiality** (data encrypted end-to-end)

# 3. HTTPS — SSL/TLS Layer (Very high-yield)

HTTPS = HTTP + TLS/SSL.

### 3.1 Why HTTPS is required

- Prevents **packet sniffing**
    
- Prevents **MITM attacks** (Man-in-the-middle)
    
- Ensures **authentication** of server
    
- Ensures **data integrity**
    
- Required for: login pages, payment gateways, cookies with secure flag, APIs
    

### 3.2 How HTTPS works (short 7-mark explanation)

1. Client → Server: “Hello” with supported cipher suites
    
2. Server → Client: sends **SSL certificate** containing public key
    
3. Client verifies certificate via Certificate Authority (CA)
    
4. Client generates a **session key**, encrypts it with server’s public key, sends it
    
5. Server decrypts with its private key
    
6. Both now share the same symmetric key → secure communication
    

### 3.3 SSL Certificate Contents

- Public key
    
- Server domain
    
- Issuer (CA)
    
- Validity period
    
- Certificate signature

# 4. Common Web Security Threats (must memorise for long answers)

## 4.1 XSS — Cross-Site Scripting

Occurs when untrusted input is inserted into a webpage without proper escaping.

### Types:

- **Stored XSS** — malicious script stored in DB
    
- **Reflected XSS** — script returned in HTTP response
    
- **DOM-based XSS** — client-side JS modifies DOM insecurely
    

### Prevention:

- Escape output: `htmlspecialchars()`
    
- Validate/sanitize input
    
- Use Content-Security-Policy (CSP) header:  
    `Content-Security-Policy: default-src 'self'`
    

---

## 4.2 CSRF — Cross-Site Request Forgery

Attacker tricks user into performing action (e.g., money transfer).

### Prevention:

- CSRF tokens in forms
    
- SameSite cookies
    
- Double-submit cookies
    
- Check referer/origin headers
    

---

## 4.3 SQL Injection

Attacker manipulates queries by injecting rogue input.

### Prevention:

- Prepared statements
    
- Input validation
    
- Least-privilege DB accounts
    

---

## 4.4 Session Hijacking

Attacker steals session ID (cookie theft, sniffing, MITM).

### Prevention:

- HTTPS only
    
- `HttpOnly` cookies
    
- `Secure` cookies
    
- Regenerate session IDs after login
    
- Short session timeouts
    

---

## 4.5 Clickjacking

Attacker loads website in hidden iframe.

### Prevention:

- `X-Frame-Options: DENY`
    
- `Content-Security-Policy: frame-ancestors 'none'`

# 5. State Management: Cookies vs Sessions

(Asked repeatedly in KTU exams)

## 5.1 Cookies

Small data stored on client browser.

### Characteristics

- Client-side
    
- Max ~4 KB
    
- Sent on each request
    
- Useful for preferences, low-security state
    
- Can be read/modified by browser (unless HttpOnly set)
    

### Key Attributes

- `expires`, `max-age` — expiration
    
- `domain`, `path` — scope
    
- `secure` — only sent over HTTPS
    
- `httponly` — not accessible by JavaScript
    
- `samesite` — protects against CSRF
    

---

## 5.2 Sessions

Server-side storage. Client only holds session ID.

### Characteristics

- Secure (data not stored in browser)
    
- Used for authentication
    
- Larger storage possible
    
- Requires session cookie (ID)
    

---

## 5.3 Compare Cookies vs Sessions (write-for-exam)

|Feature|Cookies|Sessions|
|---|---|---|
|Storage|Client|Server|
|Security|Low|High|
|Capacity|~4 KB|Large|
|Lifetime|Long-term possible|Ends when browser closed/timeout|
|Use-cases|Preferences, tracking|Auth, user data|

# 6. HTTP Caching — Very important (KTU frequently asks caching headers)

Caching improves performance by reducing repeated requests.

### Types of caching:

1. **Browser Cache**
    
2. **Proxy Cache**
    
3. **CDN Cache**
    

### Cached Elements

- HTML, CSS, JS
    
- Images, icons, fonts
    
- API responses (controlled via headers)
    

---

## 6.1 Cache-Control header (memorise this!)

```
Cache-Control: public
Cache-Control: private
Cache-Control: no-cache
Cache-Control: no-store
Cache-Control: max-age=3600
Cache-Control: must-revalidate
```

### Meaning:

- **public** — can be cached by browser + proxy
    
- **private** — cached only by browser
    
- **no-cache** — must validate with server before using cached copy
    
- **no-store** — must not store at all (high security pages, banking)
    
- **max-age** — time in seconds to keep cached
    
- **must-revalidate** — browser must confirm expiration
    

---

## 6.2 ETag and Last-Modified validation

### ETag

A server-generated fingerprint used for cache validation.

```
ETag: "abcxyz"
If-None-Match: "abcxyz"
```

If matched → server returns `304 Not Modified`.

### Last-Modified

```
Last-Modified: Tue, 20 Sep 2024 10:00:00 GMT
If-Modified-Since: Tue, 20 Sep 2024 10:00:00 GMT
```

---

## 6.3 Expires header (older method)

```
Expires: Wed, 21 Oct 2025 07:28:00 GMT
```

Replaced by `Cache-Control: max-age`.

# 7. Important Security-Related HTTP Headers

1. **Content-Security-Policy (CSP)**  
    Mitigates XSS by restricting allowed scripts.
    
2. **X-Frame-Options**  
    Prevents clickjacking (`DENY`, `SAMEORIGIN`).
    
3. **Strict-Transport-Security (HSTS)**  
    Forces HTTPS:  
    `Strict-Transport-Security: max-age=31536000`
    
4. **X-Content-Type-Options**  
    Prevent MIME sniffing:  
    `X-Content-Type-Options: nosniff`
    
5. **Referrer-Policy**  
    Controls referrer data leakage.
    
6. **Set-Cookie** (with security flags)
    
    ```
    Set-Cookie: session=xyz; HttpOnly; Secure; SameSite=Strict
    ```

# 8. Short Notes (3–5 mark ready)

- **Idempotent HTTP Methods**  
    GET, HEAD, PUT are idempotent. POST is not.
    
- **Statelessness of HTTP**  
    Each request independent; server stores no client state unless cookies/sessions added.
    
- **SameSite Cookie Attribute**  
    Protects against CSRF by controlling cross-site cookie sending.
    
- **HTTPS advantages**  
    Confidentiality, integrity, authentication.

### PYQ 1 — GET vs POST (3 marks)

**GET**

- Data appended to URL (visible).
    
- Used for retrieval, search, idempotent operations.
    
- Limited data length.
    
- Can be bookmarked and cached.
    

**POST**

- Data sent in request body (not visible).
    
- Used for form submission, login, file upload.
    
- No size limit.
    
- More secure than GET.
