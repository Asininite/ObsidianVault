# Introduction to Prometheus

## 1. What is Prometheus?

- **Definition:** An open-source, highly reliable monitoring and alerting solution originally built by SoundCloud.
    
- **Target Systems:** Used to monitor servers, virtual machines (VMs), databases, and dynamic microservices.
    
- **Key Capabilities:**
    
    - Tracks, analyzes, and reports system health, performance, and application behavior.
        
    - Maintains a multi-dimensional data model with time-series data identified by metric names and key-value pairs (labels).
        
    - Queries data using **PromQL (Prometheus Query Language)**.
        
    - Integrates with **Alertmanager** for proactive, flexible notification management.
        

## 2. Core Architecture & Mechanics: How It Works

Unlike many monitoring tools that wait for applications to push metrics, Prometheus primarily utilizes a **pull-based (scraping) model**.

```
[ Target Applications ] <── (Pulls plain-text metrics via HTTP/S) ── [ Prometheus Server ]
                                                                             │
                                                                       (Sends Alerts)
                                                                             ▼
[ Notifications (Email, Slack, etc.) ] <───────────────────────────── [ Alertmanager ]
```

### The Scraping Lifecycle

1. **Service Discovery:** Prometheus dynamically discovers active services running across your infrastructure or reads a manually defined list of target services.
    
2. **Scrape/Pull:** At defined intervals, Prometheus sends HTTP/HTTPS requests to the target endpoints.
    
3. **Exposition Format:** Targets expose their metrics in a standardized, plain-text format.
    
4. **Ingestion & Timestamping:** Prometheus scrapes the real-time metrics, attaches unique identifiers (labels) and timestamps, organizes and compresses the data, and stores it.
    
5. **Autonomy:** Prometheus servers are completely autonomous. They do not rely on networked storage, distributed storage, or external services to function, making them highly resilient during outages.
    

## 3. Gathering Metrics: Instrumentation & Exporters

Metrics do not automatically generate themselves; they must be exposed by your system or code. This is accomplished using two primary methods:

### A. Direct Instrumentation

Developers write instrumentation directly into the application's source code to produce custom metrics.

- **Client Libraries:** With just two or three lines of code, a developer can define a metric using a Prometheus client library.
    
- **Supported Languages:**
    
    - _Official:_ Go, Python, and Ruby.
        
    - _Third-Party:_ C++, .NET, Node.js, Haskell, Erlang, Rust, Java, and Scala.
        

### B. Exporters

If you cannot modify the source code of an application (e.g., a third-party database or legacy software), you deploy an **Exporter** alongside it.

- **Role:** Acts as a one-to-one proxy.
    
- **Mechanism:** It queries the application’s native metrics interface, transforms that raw data into the standard Prometheus exposition text format, and returns it when the Prometheus server scrapes the exporter.
    

## 4. Storage & Integrations

- **Time-Series Database (TSDB):** Prometheus stores data locally in a highly compressed time-series format. This design simplifies taking incremental backups of your monitoring history.
    
- **Dedicated External Storage:** For massive enterprises, some Prometheus implementations can utilize a dedicated, external time-series database for long-term metrics storage rather than relying solely on the Prometheus server itself.
    
- **Persistence Layer Scraping:** Prometheus can scrape data from the application's persistence layer, which acts as the intermediary between the application logic and relational databases.
    
- **Native Support (No Agents Required):** Several modern platforms natively expose Prometheus metrics without needing an external exporter or software agent. Examples include:
    
    - Kubernetes
        
    - etcd
        
    - SkyDNS
        
- **Visualization:** Prometheus is typically paired with **Grafana** to design rich, customizable real-time dashboards.
    

## 5. Alerting & Alertmanager

Prometheus decouples metric evaluation from alert routing:

1. **Condition Evaluation:** The Prometheus server constantly evaluates metric rules against its data.
    
2. **Alert Generation:** When an alert threshold is breached, the Prometheus server generates an alert and forwards it to **Alertmanager**.
    
3. **Alert Routing & Deduplication:** Alertmanager manages, deduplicates, groups, and routes these alerts to the correct escalation channels, such as email, on-call paging systems, and chat platforms.
    

## Quick Revision Questions & Answers

**1. What is the fundamental difference between Prometheus's metrics collection model and a traditional "push" monitoring model?**

- **Answer:** Prometheus uses a pull model (scraping). Instead of applications sending metrics to a central server on their own schedules, the Prometheus server proactively sends HTTP/HTTPS requests to predefined endpoints to pull down text-based metrics at designated intervals.
    

**2. What is the difference between "direct instrumentation" and using a Prometheus "exporter"?**

- **Answer:** Direct instrumentation involves writing Prometheus client library code directly inside the application's source code. An exporter is a separate, sidecar software proxy deployed next to a third-party application (like a database) to translate its native metrics into Prometheus's plain-text format.
    

**3. Why are Prometheus servers described as "autonomous"?**

- **Answer:** Because each server runs independently with its own local storage, scraping configuration, and database engine. They do not rely on external network storage or remote services to perform their core duties, making them highly reliable during massive network outages.
    

**4. What role does Alertmanager play in a Prometheus ecosystem?**

- **Answer:** Prometheus evaluates metric thresholds and triggers alerts, but it delegates the routing to Alertmanager. Alertmanager deduplicates, silences, groups, and routes these notifications to proper destinations (e.g., Slack, email, PagerDuty) according to on-call schedules.
    

**5. Which visualization tool is Prometheus most commonly paired with in production environments?**

- **Answer:** **Grafana** is the industry-standard visualization tool used alongside Prometheus to query TSDB data and render real-time dashboards.
