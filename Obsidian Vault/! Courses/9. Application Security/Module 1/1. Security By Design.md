# Security by Design and the Secure SDLC

## 1. The Philosophy of Security by Design

- **The Problem:** Historically, security was treated as an afterthought in software development. Teams would build the entire application and only hand it over to security just before launch. This often resulted in delayed launches, broken code, or compromised servers.
    
- **The Solution (Security by Design):** Security must be integrated from the very beginning. This requires solid, early, and regular collaboration between the development (Dev) and security (Sec) teams to ensure code is written securely from day one.
    

> **Deep Dive: "Shifting Left"**
> 
> In the DevOps industry, the practice of moving security tasks to the very beginning of the development lifecycle is commonly called **"Shifting Left"** (since you are moving tasks to the left side of a traditional timeline or Kanban board).

## 2. The Standard SDLC (Software Development Lifecycle)

The SDLC is a well-structured framework that details the strategy for developing, deploying, and maintaining high-quality software. It consists of five traditional stages:

1. **Requirements:** Comprehending customer expectations and project needs.
    
2. **Design:** Making architectural decisions based on the requirements.
    
3. **Develop:** Writing the code and putting the design into action.
    
4. **Test:** Verifying that the code meets client needs and functions smoothly.
    
5. **Deploy:** Releasing the fully tested product to live production.
    

## 3. The Secure SDLC

A Secure SDLC explicitly describes how security practices fit into the existing development model. The core processes involved include:

- Risk assessment
    
- Threat modeling and design review
    
- Static analysis
    
- Security testing and code review
    
- Security assessment and configuration
    

## 4. Mapping DevOps into the Secure SDLC

By integrating security directly into DevOps workflows (often referred to as **DevSecOps**), teams can secure their deployment pipelines. Here is how security maps to each specific phase:

### A. Requirements Phase

- **Risk Assessment:** Evaluate the type of information the application will handle (e.g., credit cards vs. public blog posts) and determine the necessary security standards.
    
- **Attack Profiling:** Consider exactly how people might attempt to attack the application and identify the specific information that must be protected.
    

### B. Design Phase

- **Design Threat Modeling:** Ask critical questions: _What elements make this architecture vulnerable?_ _How can we design precautions into the system right now?_
    
- **Pipeline Security:** Ensure the CI/CD (Continuous Integration/Continuous Delivery) pipeline itself is secure and automatically searching for vulnerabilities.
    

### C. Develop Phase

- **Static Analysis:** Use automated tools to scan the raw source code for known security vulnerabilities before the code is even run.
    
- **Data Validation:** Incorporate automated data validation to guarantee that any information entering the system is correct, useful, and not malicious (like SQL injection attempts).
    
- **Secure Scrum:** A variation of the agile Scrum framework that specifically emphasizes security tasks throughout the sprint.
    

> **Deep Dive: SAST Tools**
> 
> The "Static Analysis" mentioned here is known in the industry as **SAST (Static Application Security Testing)**. SAST tools act like a spell-checker for security, scanning your raw code as you type it to find hardcoded passwords or insecure functions.

### D. Test Phase

- **Incorporate Vulnerability Scans:** Run automated security testing on the compiled code.
    
- **Strive for Failure:** Adopt a hacker's mindset. If your own QA team can break the application, malicious attackers definitely will be able to.
    
- **Parallelize Security Testing:** Do not wait until functional testing is done to start security testing. Run code scanners _at the exact same time_ as your Unit Tests and Functional Verification Tests (FVTs) to save time and shorten the test window.
    

### E. Deploy Phase

When the code is in production, you must ensure it continues to function safely.

- **Automated Deployment & Rollbacks:** If a bad or compromised deployment goes live, automated rollback scripts must be in place to instantly revert changes (e.g., erasing a newly uploaded malicious file or undoing a bad configuration).
    
- **Production Security Tests:** Imitate real-world hacking methods against the live application to reveal hidden flaws.
    

> **Deep Dive: Penetration Testing**
> 
> The "production security tests" mentioned above are commonly referred to as **Penetration Testing (Pen Testing)** or **Red Teaming**. Ethical hackers are hired to actively try and break into the live production system to find gaps that automated scanners missed.

## Quick Revision Questions & Answers

**1. Why is treating security as an "afterthought" dangerous?**

- **Answer:** Because discovering security flaws at the end of the development cycle often requires rewriting core parts of the application, leading to delayed launches or deploying vulnerable code that can be easily cracked.
    

**2. What is "Threat Modeling" and in which SDLC phase does it primarily occur?**

- **Answer:** Threat modeling is the process of identifying architectural vulnerabilities and planning precautions against them. It occurs during the **Design** phase.
    

**3. What is the purpose of Static Analysis during the Develop stage?**

- **Answer:** To use automated tools to read the raw source code and identify security vulnerabilities or insecure coding practices before the application is even compiled or run.
    

**4. How does "parallelizing" tests help the DevOps pipeline?**

- **Answer:** By running security vulnerability scans at the exact same time as functional and unit tests, teams can drastically shorten the overall testing window and save time.
    

**5. What is the purpose of an automated "rollback" during the Deploy phase?**

- **Answer:** If a newly deployed version of the application contains a critical flaw or security risk, a rollback automatically reverts the system back to the previous stable state, undoing the bad modifications instantly.
