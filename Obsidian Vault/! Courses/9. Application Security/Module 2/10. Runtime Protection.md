# Runtime Protection: IAST and RASP

## 1. What is Runtime Protection?
*   **Definition:** A modern security mechanism that shields applications against threats and vulnerabilities while the application is actively running.
*   **Purpose:** Traditional security scans (like static analysis) happen on dormant code. Runtime protection evaluates how the code *actually behaves* when it is live and executing.

---

## 2. Interactive Application Security Testing (IAST)
*   **When:** Used during the **testing process** (pre-release).
*   **Purpose:** To detect security flaws in real-time before the application is released to the public. It provides developers with critical information about *where* to find a problem so it can be fixed immediately.
*   **Key Features:**
    *   **Low False-Positives:** It examines the application in real-time, which typically results in fewer false alerts.
    *   **CI/CD Integration:** Easily connects with standard build, test, and QA tools (like Docker).
    *   **Cost-Efficient:** Because it finds bugs early in the lifecycle (while the developer is still working closely with the code), it is much cheaper and faster to fix than errors found in production.
    *   **Scalability:** Scales well across enterprise domains.

## 3. Runtime Application Self-Protection (RASP)
*   **When:** Used in the **production environment** (post-release).
*   **Purpose:** To provide runtime-level protection by safeguarding software from harmful inputs based on the program's behavior and the context of the activity.
*   **Key Features:**
    *   **Real-time Prevention:** Identifies and prevents assaults (like SQL injection, exploits, or bots) in real-time *without requiring human involvement*.
    *   **Self-Protecting:** It is integrated directly into the application, allowing it to monitor itself.
    *   **Session Control:** If RASP senses a threat, it can automatically terminate the user's session and notify the security team.
    *   **Cloud Compatibility:** It is highly compatible with cloud computing, where applications run on infrastructure outside of your internal secure network.

---

## Summary Comparison

| Feature | IAST | RASP |
| :--- | :--- | :--- |
| **Phase** | Testing/QA | Production (Live) |
| **Primary Goal** | Find and fix flaws *before* release. | Prevent and block attacks *after* release. |
| **Human Action** | Requires developer to fix the bug. | Operates automatically (self-protecting). |
| **Key Capability** | Real-time feedback for faster debugging. | Real-time traffic interception (SQLi, bots). |

## Quick Revision Questions & Answers

**1. Why is IAST considered "less expensive" than finding vulnerabilities in production?**
*   **Answer:** IAST detects vulnerabilities early in the development lifecycle while the developer is still working closely with the code, making the fixes much cheaper in terms of resources and security risk compared to fixing a production breach.

**2. In which environment should you deploy RASP?**
*   **Answer:** In the production environment, where it can provide active protection against live threats.

**3. What happens if RASP detects a malicious user session?**
*   **Answer:** It can automatically terminate the user's session and notify the security team of the potential threat.

**4. Why is RASP particularly useful for cloud-based applications?**
*   **Answer:** Securing the cloud is difficult because apps run on infrastructure outside your private network. RASP is inherently compatible with cloud environments, providing a "shield" that lives inside the application itself.

**5. Which tool—IAST or RASP—is used to simulate and block active traffic, such as SQL injection, in real-time?**
*   **Answer:** RASP.
