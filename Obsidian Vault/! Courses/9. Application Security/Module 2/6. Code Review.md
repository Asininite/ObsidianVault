# Secure Code Review

## 1. Introduction to Code Review
*   **Definition:** Code review is a critical component of security testing within the DevOps community. It involves examining the application's source code to find existing security flaws, logic errors, or vulnerabilities.
*   **The Focus:** The primary focus is on identifying exposed threats within the code and scrutinizing any security-critical components.
*   **What it Looks For:**
    *   Logic flaws (errors in how the program thinks or processes data).
    *   Reviewing if the specification (spec) was implemented correctly.
    *   Verifying adherence to established coding style rules.
*   **Timing:** While it can be implemented at any stage of the SDLC, it is most effective when performed **early** in the development process, as bugs are easiest and cheapest to address as soon as they are written.

## 2. Types of Code Review
Effective security testing utilizes a combination of two distinct review types:

### A. Automated Code Review
*   **Best Use Case:** Essential for large codebases with many files and lengthy code, where human review would be too slow. It evaluates code fast and efficiently.
*   **Workflow Integration:**
    *   **While Coding:** Developers can use free or paid automated tools to uncover vulnerabilities in real-time as they type, allowing for immediate changes.
    *   **Continuous Integration (CI):** Automatic code scanning is used as a validation check/gatekeeper. The code must pass this scan before a pull request can be merged into the main branch.
*   **Tools:** Advanced development teams heavily utilize **SAST (Static Application Security Testing)** tools for automated reviews. These tools provide extra inputs and catch vulnerabilities before code is even checked in.

### B. Manual Code Review
*   **The Benefit:** Manual reviews frequently detect complex problems, context-specific logic errors, and nuances that automated tests and scanners completely overlook.
*   **The Requirement:** It requires a senior or highly experienced developer. They must physically read and comprehend the application's complicated control and logic flows.
*   **The Drawback:** Because it requires deep human comprehension, it is very **time-consuming**.
*   **Consistency:** Because different developers might write varying test cases, manual review ensures consistency by enforcing established policies. It also allows senior developers to point out where existing, secure libraries could be used instead of writing custom (and potentially flawed) code.

## 3. Best Practice: The Pull Request Rule
*   **The Golden Rule:** You must manually review code at *every* single pull request and comment on any issues immediately.
*   **Why?** It is drastically easier and more effective for a senior developer to review 50 to 100 lines of fresh code in an immediate pull request than it is to wait and try to review thousands of lines of code weeks later when the context has been forgotten.

## Quick Revision Questions & Answers

**1. What is the primary focus of a secure code review?**
*   **Answer:** To find existing security flaws, vulnerabilities, and logic errors, specifically focusing on exposed threats and security-critical components of the source code.

**2. Why is automated code review heavily utilized during Continuous Integration (CI)?**
*   **Answer:** It acts as an automated validation check. It scans the code fast and efficiently to ensure no known vulnerabilities are merged into the main branch from a pull request.

**3. What is the major drawback of manual code review?**
*   **Answer:** It is highly time-consuming because it requires an experienced developer to read and comprehend complicated control and logic flows.

**4. Why is manual code review still necessary if automated SAST tools are being used?**
*   **Answer:** Manual reviews can detect complex logic flaws and context-specific problems that automated tests and scanners frequently overlook.

**5. What is the "golden rule" regarding when manual reviews should happen to save time and effort?**
*   **Answer:** They should happen at every single pull request (reviewing small chunks of 50-100 lines) rather than waiting to review thousands of lines weeks later.
