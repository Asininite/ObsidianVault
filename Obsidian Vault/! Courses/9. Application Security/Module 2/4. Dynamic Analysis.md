# Dynamic Analysis and DAST

## 1. What is Dynamic Analysis?
*   **Definition:** Dynamic analysis is the process of testing and evaluating an application *while it is executing* (running).
*   **Target:** It is typically run against fully built, complete applications.
*   **Timing:** While static analysis (SAST) occurs during early development, dynamic analysis occurs later in the pipeline: during staging, pre-production, or even after code is deployed to production.
*   **Real-time focus:** It jumps right into real-time, active situations, eliminating the need to artificially create isolated test scenarios.
*   **Key Discoveries:** It helps identify active vulnerabilities, memory leakage issues, and potential crashes that only manifest when the application is running in a live production environment.

## 2. What is DAST?
*   **Definition:** DAST stands for **Dynamic Application Security Testing**.
*   **The Perspective:** It evaluates the application "from the outside in," usually through the front-end interface, simulating a real user or attacker.
*   **"Black-Box" Testing:** DAST is not functional testing. It acts exactly like a malicious attacker. It performs black-box testing, meaning it has *no access* to the internal source code. It only analyzes the behaviors of the application based on the inputs it provides and the outputs it receives.

## 3. The Three Key Benefits of Dynamic Analysis

### A. Crawling the Interface
*   Dynamic analysis tools "crawl" an application's interface dynamically, usually starting from the root URL.
*   This intentional attempt to break into the system gives developers the upper hand, allowing them to identify live breakpoints and vulnerabilities from an attacker's exact perspective so they can patch them before real attackers find them.

### B. Performing Insightful Tests on Behavior
*   The tests show exactly how the running application reacts to various simulated inputs (e.g., actions made via a URL or a form submission).
*   *Safety Note:* Because these simulated inputs can be malicious or chaotic, you must ensure they don't harm your real production data. It is highly recommended to use a **dummy database** when running these dynamic tests.
*   The results reveal whether the code performs as intended, crashes, throws unexpected errors, or executes improperly when fed unexpected data.

### C. Flushing Out Faults in Dynamic Code Paths
*   Because the code is being tested while physically running, it exposes faults in *dynamic* code paths that static analyzers might completely miss (since static analyzers only look at dormant code).
*   It provides real, accurate results about how the application behaves under pressure, making it much easier to locate and understand the exact changes needed to secure the live environment.

## Quick Revision Questions & Answers

**1. What is the fundamental difference in timing between Static Analysis and Dynamic Analysis?**
*   **Answer:** Static analysis is performed early during development on raw source code. Dynamic analysis is performed later (staging, pre-prod, or production) on a fully built, running application.

**2. Why is DAST considered "Black-Box" testing?**
*   **Answer:** Because the DAST tool operates from the outside (like an attacker) and does not have any access to the internal source code. It only looks at the inputs it sends and the outputs the application returns.

**3. What critical safety precaution should you take before running dynamic analysis tests that simulate malicious inputs?**
*   **Answer:** You should use a dummy database, rather than your real-time production database, to prevent the simulated attacks from corrupting or harming actual data.

**4. What does DAST stand for?**
*   **Answer:** Dynamic Application Security Testing.

**5. Why can dynamic analysis find errors that static analysis misses?**
*   **Answer:** Because it tests the code while it is actively running, allowing it to flush out faults in dynamic code paths and memory usage that aren't visible when the code is just sitting dormant on a file system.
