# OWASP Top 1-3: Critical Vulnerabilities
![[Pasted image 20260705000643.png]]


## 1. Broken Access Control (Ranked #1)
Access control ensures users can only access the resources they have permission to use. "Broken" access control occurs when users can perform actions or access data outside their intended permissions.

*   **The Risk:** Attackers often tamper with elements like IDs visible in a URL to see if they can access another user's data. This leads to information disclosure, unauthorized data modification, or total account compromise.
*   **Prevention Strategies:**
    *   **Principle of Least Privilege:** Assign the absolute minimum privileges required for a user's role.
    *   **Regular Audits:** Perform consistent access control checks (both horizontally and vertically) to ensure permissions are up to date.
    *   **Limit Public Information:** Only expose data that is strictly necessary for the application to function.
    *   **Disable Directory Listings:** Prevent web servers from listing directory contents, which stops attackers from mapping your server's file structure.
    *   **Monitoring:** Log all access control failures and configure alerts for system administrators to investigate them immediately.

## 2. Cryptographic Failures (Formerly Sensitive Data Exposure)

![[Pasted image 20260705000752.png]]

This vulnerability occurs when sensitive data (like credit card numbers or IDs) is not adequately protected during storage or transmission.

*   **The Risk:** Using weak, old, or "traditional" encryption that is easily broken. Using insecure protocols like SMTP or FTP leaves data vulnerable to "Man-in-the-Middle" (MitM) attacks.
*   **Prevention Strategies:**
    *   **Authenticated Encryption:** Use modern, authenticated encryption rather than weak, outdated methods.
    *   **Encryption In-Transit & At-Rest:** Ensure all sensitive data is encrypted while being transmitted and while stored in databases.
    *   **Always use HTTPS:** Never use HTTP, as it transmits data in plain text.
    *   **Key Management:** 
        *   **NEVER hardcode** encryption keys in your source code.
        *   Limit keys to a single purpose.
        *   Follow a strict key lifecycle and management process, including secure backups.

## 3. Injection
Injection occurs when untrusted or "hostile" data is sent to an interpreter (like a database or shell) as part of a command or query. The interpreter is tricked into executing unintended commands.

![[Pasted image 20260705000808.png]]
![[Pasted image 20260705000817.png]]

*   **Common Types:** SQL Injection, OS Command Injection, HTTP Host Header Injection, LDAP Injection, and Cross-Site Scripting (XSS).
*   **Prevention Strategies:**
    *   **Use Secure APIs/Parameterized Interfaces:** The most effective defense. By using a parameterized interface, the interpreter treats user input strictly as data, never as executable code.
    *   **Sanitize Inputs:** Check all incoming data for suspicious patterns (like `SELECT` statements in input fields).
    *   **Escape Lists:** Block dangerous keywords or special characters that could be used to manipulate an interpreter. Keep these lists regularly updated.

## Quick Revision Questions & Answers

**1. Which vulnerability is currently ranked as the #1 threat in the OWASP Top 10?**
*   **Answer:** Broken Access Control.

**2. What is the danger of leaving web server directory listings enabled?**
*   **Answer:** It acts as an open invitation for hackers to see the internal structure of your web server's directory and identify files to target.

**3. Why should you avoid using SMTP and FTP protocols for sensitive data?**
*   **Answer:** They are old, insecure protocols that are highly susceptible to "Man-in-the-Middle" attacks.

**4. What is the "golden rule" of handling encryption keys?**
*   **Answer:** Never hardcode them in your software application. They must be managed through a secure lifecycle process.

**5. What is the most effective way to eliminate the risk of Injection attacks?**
*   **Answer:** Using a secure API that provides a parameterized interface. This forces the interpreter to treat user input as data rather than as an executable command.

# OWASP Top 4-6: Vulnerability Analysis

## 1. Insecure Design (#4)
*   **Definition:** Refers to the lack of effective security controls during the **design phase** of an application. 
*   **The Risk:** Even a "perfectly implemented" code structure cannot fix a fundamentally unsafe architectural design. It leaves the app without basic defenses like brute-force protection or firewalls.
*   **Crucial Focus: Proper Error Handling:**
    *   **The Problem:** Improper error handling often leaks sensitive information (server software versions, file paths, directory structures, or database table structures), which provides attackers with a "roadmap" for SQL injection or other exploits.
    *   **Best Practice:**
        *   Display **user-friendly, generic messages** to the UI (e.g., "Username or password incorrect" rather than "Password incorrect").
        *   Log the **detailed technical error** internally for troubleshooting, but never expose it to the user.

## 2. Security Misconfiguration (#5)
*   **Definition:** Overlooked configuration weaknesses that exist in an application.
*   **The Risk:** Often occurs when developer-specific features (like debug mode, QA features, or default admin accounts) are left active in a live production environment. This can lead to unauthorized access or privilege escalation.
*   **Best Practice (The "Cleaning" Strategy):**
    *   **Principle of Least Privilege (PoLP):** Users should only have the minimum permissions necessary to perform their specific tasks.
    *   **Pruning:** Actively remove unused frameworks, features, documentation, and backdoor accounts.
    *   **Default Awareness:** Always check for and change default usernames/passwords immediately.
    *   **Full Stack Responsibility:** Security misconfiguration can happen anywhere—not just the app code. Secure the entire stack: Platform, Web Server, App Server, and Database. This is a team effort requiring both Developers and System Administrators.

## 3. Vulnerable and Outdated Components (#6)
*   **Definition:** Using core platforms, supporting frameworks, or libraries that are no longer supported or patched.
*   **The Risk:** Software evolves constantly. If you do not update dependencies, you remain vulnerable to known exploits that have already been fixed elsewhere. Unused dependencies are also a risk because they remain in your system as "ghosts" that don't add functionality but *do* add potential security flaws.
*   **Best Practice:**
    *   **Inventory Management:** Create and maintain a strict list of all installed components and nested dependencies.
    *   **Regular Patching:** Track updates and patches continuously.
    *   **Stay Informed:** Keep up to date with the latest security risks published by **OWASP** and **CISA**.

## Quick Revision Questions & Answers

**1. Why is "Insecure Design" considered a fundamental problem compared to poor implementation?**
*   **Answer:** You cannot "patch" or code your way out of a fundamentally unsafe architecture. If the design is flawed from the start, even perfect code will remain insecure.

**2. When an attacker enters an incorrect password, why is it bad to tell them *exactly* which field is wrong (e.g., "User ID not found" vs. "Password incorrect")?**
*   **Answer:** It allows the attacker to use a process of elimination to determine which part of their credentials (the username or the password) is correct, bringing them one step closer to a successful login.

**3. What is the "Principle of Least Privilege" (PoLP) as it relates to Security Misconfiguration?**
*   **Answer:** Users and applications should only be granted the absolute minimum level of permissions required to perform their specific task, and nothing more.

**4. Why are "unused dependencies" a security risk?**
*   **Answer:** They add no functionality to your application, yet they increase the attack surface. If an unused dependency has a vulnerability, it could be exploited by an attacker.

**5. Why is system administrator involvement critical for preventing Security Misconfiguration?**
*   **Answer:** Because misconfigurations can occur anywhere in the application stack (web server, database, OS), not just the application code itself. Collaboration between developers and admins ensures the *entire* stack is secure.
