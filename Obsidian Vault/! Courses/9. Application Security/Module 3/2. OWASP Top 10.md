# OWASP Top 1-3: Critical Vulnerabilities
![[Pasted image 20260705000643.png]]


## 1. Broken Access Control (Ranked #1)
Access control ensures users can only access the resources they have permission to use. "Broken" access control occurs when users can perform actions or access data outside their intended permissions.

*   **The Risk:** Attackers often tamper with elements like IDs visible in a URL to see if they can access another user's data. This leads to information disclosure, unauthorized data modification, or total account compromise.
*   **Prevention Strategies:**
    *   **Principle of Least Privilege:** Assign the absolute minimum privileges required for a user's role.
    *   **Regular Audits:** Perform consistent access control checks (both horizontally and vertically) to ensure permissions are up to date.
    *   **Limit Public Information:** Only expose data that is strictly necessary for the application to function.
    *   **Disable Directory Listings:** Prevent web servers from listing directory contents, which stops attackers from mapping your server's file structure.
    *   **Monitoring:** Log all access control failures and configure alerts for system administrators to investigate them immediately.

## 2. Cryptographic Failures (Formerly Sensitive Data Exposure)

![[Pasted image 20260705000752.png]]

This vulnerability occurs when sensitive data (like credit card numbers or IDs) is not adequately protected during storage or transmission.

*   **The Risk:** Using weak, old, or "traditional" encryption that is easily broken. Using insecure protocols like SMTP or FTP leaves data vulnerable to "Man-in-the-Middle" (MitM) attacks.
*   **Prevention Strategies:**
    *   **Authenticated Encryption:** Use modern, authenticated encryption rather than weak, outdated methods.
    *   **Encryption In-Transit & At-Rest:** Ensure all sensitive data is encrypted while being transmitted and while stored in databases.
    *   **Always use HTTPS:** Never use HTTP, as it transmits data in plain text.
    *   **Key Management:** 
        *   **NEVER hardcode** encryption keys in your source code.
        *   Limit keys to a single purpose.
        *   Follow a strict key lifecycle and management process, including secure backups.

## 3. Injection
Injection occurs when untrusted or "hostile" data is sent to an interpreter (like a database or shell) as part of a command or query. The interpreter is tricked into executing unintended commands.

![[Pasted image 20260705000808.png]]
![[Pasted image 20260705000817.png]]

*   **Common Types:** SQL Injection, OS Command Injection, HTTP Host Header Injection, LDAP Injection, and Cross-Site Scripting (XSS).
*   **Prevention Strategies:**
    *   **Use Secure APIs/Parameterized Interfaces:** The most effective defense. By using a parameterized interface, the interpreter treats user input strictly as data, never as executable code.
    *   **Sanitize Inputs:** Check all incoming data for suspicious patterns (like `SELECT` statements in input fields).
    *   **Escape Lists:** Block dangerous keywords or special characters that could be used to manipulate an interpreter. Keep these lists regularly updated.

## Quick Revision Questions & Answers

**1. Which vulnerability is currently ranked as the #1 threat in the OWASP Top 10?**
*   **Answer:** Broken Access Control.

**2. What is the danger of leaving web server directory listings enabled?**
*   **Answer:** It acts as an open invitation for hackers to see the internal structure of your web server's directory and identify files to target.

**3. Why should you avoid using SMTP and FTP protocols for sensitive data?**
*   **Answer:** They are old, insecure protocols that are highly susceptible to "Man-in-the-Middle" attacks.

**4. What is the "golden rule" of handling encryption keys?**
*   **Answer:** Never hardcode them in your software application. They must be managed through a secure lifecycle process.

**5. What is the most effective way to eliminate the risk of Injection attacks?**
*   **Answer:** Using a secure API that provides a parameterized interface. This forces the interpreter to treat user input as data rather than as an executable command.

# OWASP Top 4-6: Insecure Design, Misconfiguration, and Outdated Components

## 1. Insecure Design (Ranked #4)
*   **Definition:** Insecure design refers to a fundamental lack of effective security controls during the design phase of an application. It focuses on risks inherent in the architectural design rather than the implementation (coding).
*   **The Core Reality:** Even perfect code implementation cannot remedy an unsafe or insecure design. 
*   **Specific Vulnerabilities:** 
    *   Lack of firewalls.
    *   Absence of mechanisms to prevent brute-force attacks.
    *   OTP (One Time Password) Bypass mechanisms.
    *   Other general architectural flaws.
*   **Prevention Strategy:**
    *   Security measures must be considered and implemented during the **design phase**, not after the code is written. 
    *   Design with security in mind from the very start.

### Critical Focus: Error Handling
Error handling is essential for troubleshooting, but if handled improperly, it becomes a major vulnerability. 
*   **The Risk:** Improper error handling can reveal:
    *   Server software version details.
    *   Locations of configuration files containing credentials.
    *   Directory structures and overall system structures.
*   **Consequences:** Exposure can lead to data breaches, massive financial losses, regulatory fines, and a tarnished organizational reputation.
*   **Best Practices:**
    *   **Secure Error-Handlers:** Use secure handlers to write detailed technical error logs internally (for troubleshooting) while providing only friendly, safe messages to the end-user.
    *   **Preventing Information Disclosure:**
        *   *Scenario: Username/Password error.* Do not tell the user specifically which field is wrong. This allows an attacker to use the process of elimination to determine which part of the credential is correct. State only that the username/password combination is incorrect.
        *   *Scenario: Database failures.* Do not display database table structures in error messages. This gives attackers the exact blueprint needed to execute a SQL injection attack.

---

## 2. Security Misconfiguration (Ranked #5)
*   **Definition:** A condition where overlooked configuration weaknesses exist in an application that attackers can exploit.
*   **The Risk:** Often involves developer features (like debug modes or QA features) that are dangerously unsafe if left active in a live production environment.
*   **Consequences:** 
    *   Unauthorized access to sensitive information.
    *   Granting users elevated privileges or excessive permissions.
*   **Prevention Strategy:**
    *   **Principle of Least Privilege (PoLP):** Always grant users the minimum permissions necessary to perform a task.
    *   **Pruning:** Implement an application that is strictly free of unneeded parts, features, and documentation. Remove any unnecessary frameworks or features.
    *   **Default Checks (Design Phase):**
        *   Check for default usernames and passwords.
        *   Check for default settings and permissions.
        *   Look for backdoor accounts or configuration files stored in clear text.
    *   **Full-Stack Responsibility:** Security misconfiguration can occur in any part of the stack—the Platform, Web Server, App Server, Database, or Custom Code.
    *   **Team Effort:** Security is a collaboration. Include System Administrators in the strategy to ensure the entire stack is properly configured and kept up to date.

---

## 3. Vulnerable and Outdated Components (Ranked #6)
*   **The Context:** Technology is constantly evolving. OS platforms, hardware, frameworks, and supporting software release bugfixes, firmware updates, and patches continually.
*   **The Risk:** If you do not update the core platform, frameworks, or dependencies (both client-side and server-side), they become outdated and leave the application vulnerable. A vulnerability might exist for days or months before your app is patched.
*   **Prevention Strategy:**
    *   **Full Awareness:** You must be familiar with the exact version of every single component and **nested dependency** used in your application.
    *   **Cleanup:** Keep your application free of unused dependencies or features; they add no functionality but introduce risk if they become outdated or exploited.
    *   **Inventory & Tracking:** Create and maintain a strict list of all installed components and nested dependencies. Actively track components to stay aware of updates.
    *   **External Intelligence:** Keep informed of the latest security risks and vulnerabilities as published by **OWASP** and **CISA**.

# OWASP Top 7-10: Authentication, Integrity, Monitoring, and SSRF

## 1. Identification and Authentication Failures (#7)

This vulnerability occurs when an application improperly validates a user's identity or manages active user sessions poorly, exposing the system to automated compromises.

### Key Exploitation Mechanisms

- **Credential Stuffing:** An automated attack where a hacker obtains a list of legitimate, leaked usernames and passwords from other breaches and uses automated tools to test them across your application's login systems.
    
- **Brute Force Attacks:** Systematic, automated attempts to guess passwords or access credentials.
    
- **Session Identifier (ID) Exposure in URLs:** If session IDs are visible in the URL path, an attacker can steal the ID and easily impersonate the legitimate user. This tricks the website into believing the attacker is the authenticated user operating on their own computer, granting them full account access.
    
- **Missing or Inadequate Session Timeouts:** A session is created whenever a user logs in. If the application lacks automatic session timeouts to log users off after a period of inactivity, logged-in users who step away from their workstations leave the system open to unauthorized physical access and data breaches.
    

### Comprehensive Prevention Strategies

- **Secure the Software Supply Chain:** The software supply chain includes absolutely everything that touches your application or plays a role in its development throughout its entire lifecycle.
    
    - Use software supply chain security tools to scan all application components to guarantee they are free from known vulnerabilities.
        
    - Conduct regular reviews and checks of all configuration changes to reduce the risk of pipeline attacks.
        
- **Protect Transmissions:** Avoid transmitting any unencrypted sensitive data to untrusted sources.
    
- **Enforce Integrity Checks:** Implement digital signatures or other integrity checks to secure data and prevent tampering.
    
- **Enforce Multifactor Authentication (MFA):** Mandatory MFA is highly effective at stopping credential stuffing, brute-force attempts, and other automated attacks.
    
- **Disable Default Credentials:** Never deploy your application with default setup credentials enabled.
    
- **Deploy a Server-Side Session Manager:**
    
    - Use the manager to generate new, completely random session IDs.
        
    - Ensure session identifiers never appear in URLs.
        
    - Store session identifiers securely.
        
    - Ensure session identifiers are immediately invalidated upon logging out, as well as when idle or absolute timeouts are reached.
        

## 2. Software and Data Integrity Failures (#8)

These failures are caused by code and infrastructure configurations that fail to protect against unauthorized modifications to application code, updates, or data.

### Key Risks and Vulnerability Vectors

- **Untrusted Third-Party Components:** Integrating software modules, packages, or libraries from untrusted sources introduces massive vulnerabilities into the application.
    
- **Insecure Auto-Updates:** Many modern applications contain automated update features that download and install updates to previously trusted software without performing sufficient integrity verification.
    
    - _The Threat Scenario:_ Attackers can exploit an insecure CI/CD pipeline to upload and distribute malicious updates. These poisoned updates are then automatically applied to all installations globally, leading to widespread data breaches or system takeovers.
        

### Comprehensive Prevention Strategies

- **Segregate the CI/CD Pipeline:** Properly configure and isolate your CI/CD pipeline. Ensure that access controls are accurate, restricted, and complete to protect the integrity of the code as it moves through the build and deployment processes.
    
- **Scan Software Components:** Continually use software supply chain security tools to inspect all third-party application components for known vulnerabilities.
    
- **Protect Data Outflow:** Never send unsigned, unencrypted, or serialized data to untrusted clients.
    
- **Implement Integrity Checks & Digital Signatures:** Apply digital signatures to verify that all code and incoming data originate from a legitimate, trusted source and have not been altered or tampered with in transit.
    

## 3. Security Logging and Monitoring Failures (#9)

Logging and monitoring are critical security controls necessary for detecting, understanding, and actively responding to security breaches. Inadequate implementations keep organizations entirely in the dark.

### Common Failure Points

- **Confusing or Weak Log Entries:** Logs with missing, weak, or confusing entries make troubleshooting impossible during an active incident.
    
- **Failing to Log Auditable Events:** Applications do more harm than good if they fail to record critical security-relevant events such as intrusion attempts, successful logins, and failed logins. These details must be preserved to perform forensic investigations in the event of a cyberattack.
    
- **Logs Overwritten Too Quickly:** If log retention periods are too short, logs are overwritten before a breach is noticed. If a breach occurred months ago and logs have been recycled, you may never discover when it happened, how it happened, or if it has happened again.
    
- **Lack of Active Monitoring:** Without an active monitoring system, administrators remain completely unaware of unusual trends, infrastructure issues, or active compromises. This allows attackers to dwell inside an organization's network undetected for long periods.
    

### Comprehensive Prevention Strategies

- **Establish Proper Log Configurations:** Ensure your application logs the correct information, in the proper format, at the right time.
    
- **Centralize and Back Up Logs:** Centralize all log data and create regular backups of raw log files.
    
- **Deploy a Modern Logging Stack (Stream & Visualize):**
    
    - Stream your application logs to a dedicated log collector like **Logstash**.
        
    - Store the log data in a centralized database like **Elasticsearch**.
        
    - Visualize and query logs over long retention periods using a tool like **Kibana**.
        
    - _Note:_ Cloud-native orchestration systems like Kubernetes make deploying this centralized logging architecture highly straightforward.
        
- **Log Format Standardization:** Always use standard, consistent log formats so that automated log analysis tools can easily parse them.
    
- **Log Auditable Security Events:** Ensure logs capture logins, access control modifications, and server-side input validation events.
    
- **Provide Sufficient Context:** Log entries must contain enough metadata to identify suspicious or malicious user accounts.
    
- **Establish Dashboards and Alerts:** Implement a robust monitoring system equipped with alerting thresholds, dashboards, and automated notifications so that security teams can respond instantly to anomalies.
    
- **Conduct Periodic Log Audits:** Routinely scrub through log files to audit entries for signs of attacker tampering or logfile manipulation.
    

## 4. Server-Side Request Forgery / SSRF (#10)

Server-Side Request Forgery occurs when an external attacker gains the ability to create or completely control malicious requests sent from a vulnerable application server to other internal, backend systems.

### How SSRF Works

1. An attacker attempts to connect directly to a secure internal server, but the network firewall blocks the direct connection.
    
2. The attacker discovers a public-facing web server that is vulnerable to SSRF (due to improper URL validation).
    
3. The attacker sends a request to the vulnerable web server, instructing it to fetch a resource from the internal server on the attacker's behalf.
    
4. Because the internal server trusts the public-facing web server, it fulfills the request. The SSRF attack successfully abuses this trust relationship to bypass firewalls, VPNs, and Access Control Lists (ACLs).
    
5. The compromised public-facing server is now a proxy or "instrument" for the attacker to pivot deeper into the internal network.
    

### Potential Consequences

Once an attacker exploits SSRF, they can use the compromised server to:

- Scan local or external networks for open ports.
    
- Access sensitive local files on the hosting server.
    
- Discover hidden internal IP addresses.
    
- Obtain Remote Code Execution (RCE) on backend infrastructure.
    

### The Three Types of SSRF

- **Basic (or Blind) SSRF:** The attacker provides a URL to the affected server, and the server accesses it, but no data from that URL is ever returned to the attacker's interface.
    
- **Semi-Blind SSRF:** The attacker provides a URL to the affected server, and while the full payload is not returned, some partial data or behavioral clues are exposed, helping the attacker gather intelligence.
    
- **Non-Blind SSRF (The Most Dangerous):** The attacker provides a URL/URI to the affected server, and the internal service returns the complete, raw data back to the attacker.

### Comprehensive Prevention Strategies

- **Input Sanitization & Validation:** Strictly sanitize and validate all client-supplied input data before using it to make requests.
    
- **Implement Destination Whitelists:** Enforce a strict whitelist at the application layer that restricts outgoing server-side requests only to permitted URLs, ports, and trusted destinations.
    
- **Disable HTTP Redirects:** Configure your web servers to disallow automatic HTTP redirects on outgoing requests.
    
- **Validate Outgoing Responses:** Do not allow your application to send raw, unvalidated responses from external services back to the client interface.
