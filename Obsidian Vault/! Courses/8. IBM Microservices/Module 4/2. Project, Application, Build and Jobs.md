# IBM Cloud Code Engine: Core Components

## 1. Projects

- **Definition:** A Project is a high-level grouping mechanism used to contain and manage related Code Engine resources and entities (like builds, apps, jobs, and TLS certificates).
    
- **Namespaces:** One of the most important functions of a Project is providing a **namespace**.
    
    - A namespace isolates groups of entities.
        
    - Entity names must be unique _within_ a specific namespace, but you can reuse names across _different_ namespaces.
        
- **Management & Access Control:** Projects allow administrators to manage access control, audit resource updates, and monitor total resource allocation (like overall CPU and memory usage) for all the entities grouped inside it.
    

## 2. Applications (Apps)

- **Definition:** An Application is the entity that actually runs your code to serve incoming traffic.
    
- **Communication Protocols:**
    
    - **HTTP/REST:** Standard web requests and API calls.
        
    - **WebSockets:** Code Engine natively supports WebSockets, which are TCP-based protocols used for long-running, session-based continuous communication (ideal for things like live chat applications).
        
- **Auto-Scaling:** Code Engine automatically scales the number of running application instances up during heavy traffic and **scales down to zero** when there is no incoming workload, saving resources.
    
- **Configuration:** In the Code Engine UI, you can easily view an app's live URL, check its deployment status, and configure its source (pulling from either a pre-registered container image or raw source code).
    

## 3. Builds (Image Builds)

- **Definition:** A Build is the automated mechanism used to convert your raw source code into a runnable container image.
    
- **Container Images:** A completed container image includes everything required for the app to run: executable source code, dependencies, system libraries, container engines, and configuration settings.
    
- **Workflow:** Once the Build successfully creates the container image, it can be deployed directly into Code Engine as a running Application.
    

### Deep Dive: Dockerfile vs. Cloud Native Buildpacks

When Code Engine builds your image, it offers two primary methods. Understanding the difference is crucial for a smooth deployment pipeline:

1. **Dockerfile (Manual & Granular Control):**
    
    - _What it is:_ A standard text file containing a list of explicit, step-by-step commands (e.g., "Install Ubuntu, copy these files, run this install script").
        
    - _The Pros:_ Ultimate control. You decide exactly what goes into the container and how it is structured.
        
    - _The Cons:_ Requires deep knowledge of Docker. You are responsible for manually optimizing the image size and ensuring the base images are patched against security vulnerabilities over time.
        
2. **Cloud Native Buildpacks (Automated & Intelligent):**
    
    - _What it is:_ An automated toolkit that inspects your source code, figures out what language/framework you are using, and automatically builds a production-ready image for you.
        
    - _The Pros:_ Zero configuration required. If you upload a folder with Python files and a `requirements.txt`, the buildpack automatically says, _"I see this is a Python app,"_ installs the correct Python runtime, installs the dependencies, and builds the container. It also automatically applies security patches to the underlying OS layers.
        
    - _The Cons:_ Less granular control over the exact underlying operating system environment compared to a custom Dockerfile.
        

## 4. Jobs

- **Definition:** A Job is a one-time execution of your code.
    
- **Apps vs. Jobs:** While Applications sit and wait continuously to handle incoming HTTP/WebSocket requests, Jobs are designed to spin up, run a specific task one time, and then **exit** immediately upon completion.
    
- **Configuration:** You can specify distinct workload configurations for a Job each time it is triggered, and Code Engine will spin up one or more instances to handle the workload.
    
- **Common Use Cases:**
    
    - **Data Processing:** Querying and transforming massive amounts of data in batches.
        
    - **Machine Learning:** Running heavy ML model training sequences.
        
    - **Reporting:** Automatically generating system or business reports based on a preset schedule.
        
    - **Billing:** Calculating and generating user bills at the end of a billing cycle.
        

## Quick Revision Questions & Answers

**1. What is the primary purpose of a "namespace" within a Code Engine Project?**

- **Answer:** It acts as an isolation mechanism for a group of resources. It ensures that entity names are unique within that specific project, while allowing the same names to be used in other projects.
    

**2. Which communication protocol should you use in a Code Engine Application if you are building a live chat app?**

- **Answer:** WebSockets (which provide long-running, TCP-based session communication).
    

**3. If your team does not know how to write Docker commands, what feature should you use to convert your source code into a container image?**

- **Answer:** Cloud Native Buildpacks (which automatically detect your language and build the image for you).
    

**4. What is the fundamental difference between an Application and a Job in IBM Cloud Code Engine?**

- **Answer:** An Application runs continuously to listen for and serve incoming network requests (like HTTP or WebSockets), while a Job runs a specific task once and then completely exits.
    

**5. Which Code Engine component would you use to run a scheduled task that processes monthly user invoices?**

- **Answer:** A Job (specifically, a billing/data processing Job).
