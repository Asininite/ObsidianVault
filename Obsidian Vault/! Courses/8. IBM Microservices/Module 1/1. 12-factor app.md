# The Twelve-Factor App Methodology

## 1. Introduction & Overview

- **What is it?** A set of best practices and guidelines for building modern software applications, specifically designed for **Software-as-a-Service (SaaS)** and web apps.
    
- **The Goal:** To create applications that are highly portable, resilient, scalable, and easy to maintain by multiple developers.
    
- **Relationship to Microservices:** While the 12-factor methodology is highly suited for microservices, microservices are _not_ a strict requirement. You can build a 12-factor monolithic application.
    
- **The Three Phases:** The 12 factors map directly to three phases of the software delivery lifecycle: **Code**, **Deploy**, and **Operate**.
    

## Phase 1: The CODE Factors

These factors focus on how the application's source code is structured, managed, and prepared for environments.

### Factor 1: Codebase

- **The Rule:** One codebase tracked in version control (like Git), with many deploys.
    
- **Explanation:** There must be a strict 1-to-1 relationship between an app and its codebase. You cannot have multiple codebases for one app, nor can multiple apps share the same codebase.
    
- **Environments:** While the codebase is the same, different _deploys_ (environments like Dev, Staging, Production) may have different _versions_ (commits) of that code running at any given time.
    

### Factor 2: Dependencies

- **The Rule:** Explicitly declare and isolate dependencies.
    
- **Explanation:** A 12-factor app never relies on the implicit existence of system-wide packages or tools (like assuming `curl` or `python` is pre-installed on the host machine).
    
- **Context:** You must use dependency declaration manifests (like `package.json` for Node, `requirements.txt` for Python, or `go.mod` for Go). This ensures that any new developer can clone the code, run a single build command, and have the exact environment needed.
    

### Factor 5: Build, Release, Run

- **The Rule:** Strictly separate the build and run stages.
    
- **Explanation:** 1. **Build:** Converts code and dependencies into an executable bundle (e.g., a Docker image).
    
    2. **Release:** Takes the build and combines it with the specific environment's configuration.
    
    3. **Run:** Runs the application in the execution environment.
    
- **Context:** You cannot make code changes directly at runtime (e.g., SSHing into a server to edit a script). Code changes must go back to the _Build_ stage.
    

### Factor 10: Dev/Prod Parity

- **The Rule:** Keep development, staging, and production as similar as possible.
    
- **Explanation:** Minimize the time, personnel, and tooling gaps between environments.
    
- **Context:** If Production uses a MySQL database, your local Development environment must also use MySQL (not SQLite). This prevents the classic "it works on my machine" bugs and catches environment-specific failures early.
    

## Phase 2: The DEPLOY Factors

These factors focus on how the application interacts with its environment and underlying resources.

### Factor 3: Config

- **The Rule:** Store configuration in the environment.
    
- **Explanation:** "Config" is anything that varies between deployments (like database URLs, passwords, API keys, or external service credentials).
    
- **Context:** Never hardcode configurations as constants in the source code. Instead, read them from **Environment Variables**. This allows you to promote the exact same code from Staging to Production, simply by swapping the environment variables.
    

### Factor 4: Backing Services

- **The Rule:** Treat backing services as attached resources.
    
- **Explanation:** A backing service is any service the app consumes over the network (databases, SMTP servers, caching systems).
    
- **Context:** The app should not distinguish between a locally managed database and a third-party managed database (like AWS RDS). You should be able to swap out a malfunctioning database for a new one purely by changing the resource URL in the config, without changing any code.
    

### Factor 6: Processes

- **The Rule:** Execute the app as one or more stateless processes.
    
- **Explanation:** Twelve-factor processes share absolutely nothing. Any data that needs to persist must be stored in a stateful backing service (like a database).
    
- **Context:** Never rely on "sticky sessions" or local memory/filesystems to store user data between requests. If a load balancer sends User A's second request to a different container, that container needs to be able to handle it seamlessly.
    

### Factor 7: Port Binding

- **The Rule:** Export services via port binding.
    
- **Explanation:** The app should be completely self-contained. It shouldn't rely on a runtime injection of a web server (like Tomcat or Apache) to create a web-facing service.
    
- **Context:** The application itself binds to a port (e.g., Port 3000) and listens for incoming requests. This is usually done by declaring a lightweight web server library as a dependency in the code.
    

## Phase 3: The OPERATE Factors

These factors focus on how the application runs, scales, and is maintained in a live environment.

### Factor 8: Concurrency

- **The Rule:** Scale out via the process model.
    
- **Explanation:** Because Factor 6 dictates that processes must be stateless, scaling an application becomes incredibly easy.
    
- **Context:** To handle higher load, you simply spin up _more_ identical processes (horizontal scaling). You don't need to make individual processes larger (vertical scaling) or worry about interdependencies between them.
    

### Factor 9: Disposability

- **The Rule:** Maximize robustness with fast startup and graceful shutdown.
    
- **Explanation:** Processes should start almost instantly. When told to shut down, they should cease taking new requests, finish their current requests gracefully, and then exit.
    
- **Context:** This is crucial for autoscaling and robust deployments. If a server crashes, the orchestration tool (like Kubernetes) can instantly spin up a replacement elsewhere without long delays.
    

### Factor 11: Logs

- **The Rule:** Treat logs as event streams.
    
- **Explanation:** A 12-factor app never concerns itself with routing or storing its own log files. It does not attempt to write to or manage log files on the local disk.
    
- **Context:** The app simply writes its unbuffered event stream to `stdout` (standard output). The execution environment (like Docker or Kubernetes) captures these streams, aggregates them, and forwards them to a centralized log analysis tool (like Splunk or Datadog).
    

### Factor 12: Admin Processes

- **The Rule:** Run admin/management tasks as one-off processes.
    
- **Explanation:** One-off tasks like database migrations, running console scripts, or fixing bad records should run in an identical environment to the regular long-running processes of the app.
    
- **Context:** The admin code should ship right alongside the application code to ensure it remains synchronized. You run these tasks against a specific release, using the exact same codebase and config as the live app.
