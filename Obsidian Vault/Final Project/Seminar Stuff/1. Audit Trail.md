##  Formal Definition (from the paper and NIST):
> An **audit trail** is a **time-ordered log** of system activities that can be used to **recreate and review events and actions**, especially those related to **security**, **data integrity**, or **compliance**.

## Components of an Audit Trail:
1. **Event ID** – Unique identifier for the event.
2. **Timestamp** – When the event occurred.
3. **Actor/User** – Who performed the action.
4. **Action** – What was done (e.g., file edited, transaction made).
5. **Object** – What was affected (e.g., which file, which account).
6. **Outcome** – Result of the action (success/failure).

## What are Audit Trails in Cryptography?
In **cryptography and secure systems**, an **audit trail** is a **secure log** that records all actions or changes in a system in a way that:
1. **Cannot be tampered with**
2. Can be **independently verified**
3. Provides **cryptographic assurance** of integrity, time, and origin

These are used in:
- Financial transactions
- Access logs
- Legal compliance systems
- Blockchain applications
- Secure messaging or storage systems
## Properties of a Cryptographic Audit Trail

| Property            | Description                                                             |
| ------------------- | ----------------------------------------------------------------------- |
| **Integrity**       | Entries cannot be altered without detection.                            |
| **Immutability**    | Once written, logs cannot be changed or erased.                         |
| **Traceability**    | You can trace the sequence of events and who caused them.               |
| **Non-repudiation** | Users cannot deny their actions.                                        |
| **Verifiability**   | Anyone can independently verify that the log is authentic and complete. |
## Problems with Traditional (and even Blockchain) Audit Trails
Even with blockchain, **audit trails still suffer from key limitations** — especially when it comes to **verifying entries**. Let's break that down.
### Problem 1: **Slow verification**
- Imagine a blockchain with **millions of transactions**.
- To verify if a specific document exists, you must **search through all blocks or transactions**.
- This can take **O(n)** time — which is not scalable.

Even using:
- **Database-backed indexing** → adds complexity + trust issues
- **Merkle trees** → reduces it to O(log n), but still not constant
- **Platform APIs (like Hyperledger Sawtooth)** → get slow or crash under load
> ❌ Problem: You’re spending time, memory, and network bandwidth just to **check if one thing exists**.

###  Problem 2: **Gas Cost / Resource Load**
- Every transaction or data fetch costs **CPU, RAM, bandwidth, and possibly real money** (in public blockchains).
- Performing multiple searches **overloads nodes** or causes **delays** in real-time auditing systems.
### Problem 3: **Scalability**
- As the number of records grows, so does the **time and cost of audit operations**.
- This makes audit trails **inefficient** for large systems (e.g., banks, governments, health systems).
